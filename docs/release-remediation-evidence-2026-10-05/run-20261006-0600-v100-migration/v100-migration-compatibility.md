## 3. 必须写进发布说明的迁移注意（新发现）

旧客户端的替换脚本用的是 `timeout /t 1 /nobreak`，并且**等待循环没有上界** ——
这正是本会话第 10 轮实测卡死、并已在工作区修掉的写法。机制（当时有原始进程快照）：

- `timeout` **依赖控制台输入**；脚本由无控制台的 GUI 启动器以 `UseShellExecute=false + CreateNoWindow=true` 拉起。
- **当替换脚本进程的 stdin 是一个不会关闭的管道时**（实测：xUnit/vstest 测试宿主，以及任何以重定向 stdin
  启动启动器的父进程），`timeout` 不返回 → 循环永远走不到备份/替换/校验 →
  **更新停在"正在应用更新"：不替换、不回滚、不报错**。
- **从资源管理器正常启动**的用户不受这种阻塞影响（`timeout` 会立即报错退出，循环空转但仍能完成替换）。

因此发布说明里应当写明（建议原文）：

> 从 ≤1.0.0 升级时，如果你是通过脚本/父进程（stdin 被重定向）启动的启动器，
> 更新可能长时间停在"正在应用更新"。请手动下载一次新版；新版已修复该等待写法
> （改为不依赖控制台的等待，并给等待加上界）。

这一条**只能写进发布说明**：旧客户端的代码无法再修改，我们不能替用户升级他的旧客户端。

## 5. 边界（不得过度解读）

- 本轮是**源码级**核对 + 此前的卡死复现；**没有**把真实的 v1.0.0 EXE 跑起来做一次端到端升级
  （那需要下载 43,989,943 字节的旧产物、搭本地 HTTP 清单、并让它替换自己——属于可做但更重的一步，
  且它验证的是"旧客户端的更新链路"，不是"我们要发布的这个版本"）。
- 旧客户端的网络行为（对 Gitee 404 的处理、超时）未在本轮重新执行；那些在第 5 轮的"真实网络验收"里
  对**当前**客户端做过。
- 未验证旧客户端在**没有** `fallbackUrl` 的清单下会怎样（我们的新清单在 GitHub 直链路径下不带该字段，
  但那条路径只影响新客户端自更新；旧客户端只读 Gitee 的清单，而该清单由镜像步骤写入时**带** `fallbackUrl`）。
