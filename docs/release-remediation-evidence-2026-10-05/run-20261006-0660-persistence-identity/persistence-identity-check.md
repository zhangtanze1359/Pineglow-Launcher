# 升级就位的"持久化标识"核对（第 27 轮）：配置位置、凭据名、更新源都没变

日期：2026-10-06（Asia/Hong_Kong）。方法：与本仓库本地 tag `v1.0.0`（已发布版本）源码逐项比对。
本轮**未改动任何 tracked 文件**。

## 1. 为什么先问这个

前几轮查的是"旧版本留下的**文件**会不会干扰新版"（外置 `UI/`、`apply-state.json`、残留 DLL）。
但升级路上更致命的一类问题是**持久化标识变了**：如果新版把配置目录、凭据目标名或默认更新源改了，
升级就会**静默丢掉用户的全部设置或登录状态**。这类改动在代码里往往只是一行字符串，评审时很容易漏。

## 2. 逐项核对结果（全部来自 `git show v1.0.0:…` 与工作区源码）

| 持久化标识 | v1.0.0（已发布） | 工作区（候选） | 结论 |
| --- | --- | --- | --- |
| 配置目录（非 portable） | `Path.Combine(%APPDATA%, "MCMiniLauncher")` | **同一句** | ✅ 老用户配置会被新版读到 |
| 配置目录（portable） | `<EXE 目录>/data` | **同一句** | ✅ |
| 凭据目标前缀 | `TargetPrefix = "MCMiniLauncher/"` | `SecretStoreBackend.TargetPrefix = "MCMiniLauncher/"`（Read/Write/Delete 三处都用 `TargetPrefix + name`）| ✅ 老凭据仍被找到 |
| 凭据条目名 | `MicrosoftRefreshToken`、`CurseForgeApiKey` | 同上 **＋** `ProxyPassword` | ✅ **只增不改名**，属于兼容扩展 |
| 内置默认更新源 | `https://gitee.com/ztz1359/pineglow-launcher/raw/master/update.json` | **同一字符串**；另**新增**备用源 `https://github.com/zhangtanze1359/Pineglow-Launcher/releases/latest/download/manifest.json` | ✅ 主源不变，备用源是新增（`DefaultUpdateMirrorUrls`）|

补充：当前 `SecretStore` 在注释里就写着"凭据命名/前缀/迁移策略不变"，本次核对的结论**与这句声明一致**
（声明取自 R0/R2 轮次的修复记录）。非 Windows 的受限文件后端也明确写了"键名不加 `MCMiniLauncher/` 前缀，保持落盘兼容"。

## 3. 本轮**没有**做的事（按现场保护约定）

**没有**为了"实测一次跨版本读凭据"而向 Windows 凭据管理器写入任何测试条目。
本次约定的规则是"真实配置/存档/游戏/凭据**只读**"，而写一条测试凭据就是修改真实凭据库；
另外原始评估已记录本机存在 4 条**历史**凭据条目，更不该在其旁边增删。
因此本轮结论是**源码级同一性证明**（前缀常量、条目名、P/Invoke 参数逐一相同），
而不是"用 v1.0.0 的二进制写、用新版读"的端到端演示——后者需要写真实凭据，代价与风险都不划算。

## 5. 结论

**≤1.0.0 的用户可以安全升级**：配置、凭据、更新源三条持久化链都没断，清单协议也兼容。
需要做的只有两件**发布说明**里的事（删旧 `UI/`；提示旧客户端替换脚本的卡死风险），
外加一条可选的产品取舍（是否在产品侧处理陈旧 `apply-state`）。

## 6. 边界

- 全部是**源码级**比对；没有跑真实的 v1.0.0 二进制（见 §3 的理由）。
- 未覆盖：非 Windows 的 `secrets.json` 文件后端（本机无法验证）、以及**跨版本原生 DLL 混用**的渲染正确性（第 25 轮已注明）。
- "凭据条目名只增不改"是**当前候选**相对 v1.0.0 的结论；未来版本仍需保持这条不变量——建议把它写进发布检查项。
