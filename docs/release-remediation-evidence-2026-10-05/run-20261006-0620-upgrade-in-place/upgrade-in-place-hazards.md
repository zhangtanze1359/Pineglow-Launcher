# 原地升级的两个隐患（第 25 轮）：外置 `UI/` 是**真隐患**，残留原生 DLL **不是**

日期：2026-10-06（Asia/Hong_Kong）。本轮**未改动任何 tracked 文件**。
证据：`stale-dll/ui-pages-live.json` + `console.log`（隐患 B 的九页验收）。

## 1. 问题从哪来

上一轮读了本地 `v1.0.0` tag 的源码，这轮顺着问下去：**一个"目录式"的老安装原地升级到新的单文件构建，会发生什么？**

先把"谁会踩到"说清楚（不夸大）：

| 旧安装形态 | 是否存在 | 依据 |
| --- | --- | --- |
| **发布附件**（只有 `manifest.json` + 43,989,943 B 的 EXE） | 存在，但**装不起来**：G07 实测该 EXE 冷启动即 `DllNotFoundException`（缺 Skia 原生库）| 原始评估 G07 + 公网资产清单 |
| **目录式/开发树**（`Pineglow.Launcher.exe` 旁边有 `UI/` 与原生 DLL） | 存在，且**能跑** | `v1.0.0` 的 csproj：`<Content Include="..\..\ui\**\*" Link="UI\…" CopyToOutputDirectory="PreserveNewest" />` |

⇒ 真正可能触发下面隐患的是**目录式/开发树的老安装**，不是那个本来就不工作的发布包。

## 2. 隐患 A（**已确认**）：残留的外置 `UI/` 会盖住新版本自带的界面

**机制**（当前代码，`LocalApiService.ResolveUiRoot()`）：

```
env(PINEGLOW_UI_DIR) → EXE 旁 UI/   ← 第 236 行
                     → UiBundle 解包（内嵌界面）  ← 第 245 行
                     → 配置目录 UI/     ← 第 252 行
```

**第 236 行在 245 行之前** ⇒ 只要 EXE 旁边还留着老安装的 `UI/`，新版本就会**用它**，而不是用自己内嵌的界面。
这与原始评估 R01 步骤 2 的要求（"不能新服务配旧 UI"）正面冲突。

**复现（真实产物，不是推理）**：

1. 取快照验证器发布的单文件 EXE（`5009cf73…`），放进一个干净目录 + `portable.flag`；
2. 在旁边放一个 `UI/index.html`，内容只含标记 `STALE-UI-MARKER-FROM-OLD-INSTALL`；
3. 以测试端口启动，等 `/api/health` 200；
4. `GET /index.html` → **返回的正是那个标记**（长度 104，"包含 STALE 标记? True"）。

也就是说：**升级后用户会继续看到旧界面**，而 R01/R02 修好的新视觉与资源闭包对他**没有生效**；
后端却是新的（新服务配旧界面）。

**为什么发布包不会踩到**：发布附件里没有 `UI/`，而且 `PublishSingleFile=true` 时 csproj **不再**复制外置
`UI/`（第 50 行的 `Content` 带 `Condition="'$(PublishSingleFile)' != 'true'"`）。所以这是**升级就位**特有的问题，
不是新装的问题——新装的冷启动验收（19/19）里"无外置 UI/ 目录"那条检查也正是这个语义。

**可选处置**（两条，取舍权在你）：

- **(i) 只写发布说明（零代码改动）**：明确告知"从目录式/≤1.0.0 升级后，请删除启动器旁的 `UI/` 目录；
  新版本自带界面，不再需要外置 UI"。诊断办法：启动日志里有 `[LocalApi] 监听 127.0.0.1:<port>, ui=<根路径>`
  （当前代码第 197 行仍在打），`ui=` 指到旧目录就是踩到了。
- **(ii) 产品侧修**（需授权）：当构建**内嵌**了界面时，让内嵌包优先于 EXE 旁的 `UI/`（或把陈旧目录改名让开并记日志）。
  代价：改的是核心解析路径，产物 SHA 会变、本会话全部既有证据都要重跑，且要重新评估"开发树里运行"的便利性。

## 3. 隐患 B（**已排除**）：残留的原生 DLL 不影响启动与渲染

老目录安装旁边还有 7 个原生 DLL（`libSkiaSharp.dll` 11,628,896 B、`libHarfBuzzSharp.dll` 1,816,088 B、
`av_libglesv2.dll` 5,394,096 B 等）。实测把它们**原样放在新的单文件 EXE 旁边**：

| 检查 | 结果 |
| --- | --- |
| `/api/health` | **200**（进程正常起来）|
| 九页界面运行时验收（真实 WebView2 + CDP）| **9/9 PASS**，`externalPending=0`、异常 0、console.error 0、`uiAssetFailures=0`、`productLocalFailures=0` |

⇒ 单文件 EXE 用自己的自解包原生库，旁边的陈旧 DLL **没有**造成启动或渲染问题。
**边界**：这些 DLL 与快照同属一个构建世代；**跨世代的 Skia 版本不匹配**未验证（那需要一份真正的 v1.0.0
目录式产物），所以只能说"当前世代残留无害"，不能外推为"任何残留都无害"。

## 4. 本轮改变了什么

- "旧版迁移"多了一条**必须写进发布说明**的操作：升级后删掉旧 `UI/`（并给了日志诊断法）。
- 多了一个**可选的代码级处置**（内嵌包优先），连同它的代价（产物 SHA 变、全部证据重跑）一起交给你决定。
- 隐患 B 被实测排除，不再需要用户为此做任何事。
