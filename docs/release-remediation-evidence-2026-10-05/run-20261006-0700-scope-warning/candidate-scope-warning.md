## 3. 关键事实：两个域**无法切分**

整改与既有功能**共享同一批文件**，所以不能"只发整改、不带功能"：

- `LocalApiService.cs`（+3430 行）里**同时**有：
  - 功能侧：`NewsImageProxyService`（第 74 行）、`/skin-image` 与 `/api/content/icon` 的令牌校验（第 360–362 行）；
  - 整改侧：`ResolveUiRoot()` / `UiRoot`（第 190、228 行）、R01 的内嵌包注释（第 242 行）。
- `ui/js/launcher.js`（+2531 行）同理：R03 的更新提示与功能界面在同一文件里。

也就是说：**发这个候选 = 同时发出那 ≥9,400 行未经复核的功能代码**（第 31 轮更正）；
要只发整改，得把这些文件按 hunk 拆开——那既违背本轮"不 reset/不 checkout"的现场约定，
也会让"已验证的字节"与"提交的字节"再次错位。

## 4. 这让发布决定变成三个问题（而不是一个）

1. **R01–R06 是否关闭？** —— 4 类已关闭、R03 客户端侧已关闭、R06 三段已验（本会话结论）。
2. **那些既有功能改动要不要一起发？依据是什么？** —— 本轮**没有**复核它们；
   "跑过测试"只覆盖到有测试的部分，不等于功能被验收。
3. **R06 的 NOT_RUN 项要不要在发布前补？** —— 它们正是第 2 条里那些功能的真机验收；
   不补就等于"发了但没在真机上验过"。

我的看法（只作建议）：第 2 条是**决定性的**（量级：≥9,400 行，见 recount §3）。要么接受"功能随整改一起发、其真机验收记为 NOT_RUN 并在发布说明里声明范围"，
要么先把功能域单独做一轮验收（那是比本会话更大的工作量，且需要真实的账号/游戏环境）。
第 3 条无论怎么选，**发布说明里都必须如实写出"哪些功能未在真机验收"**。
