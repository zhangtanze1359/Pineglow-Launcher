# 升级就位留下的"陈旧状态"（第 26 轮）：`apply-state.json` 会被原样继承

日期：2026-10-06（Asia/Hong_Kong）。本轮**未改动任何 tracked 文件**。

## 1. 问题

上一轮确认了"外置 `UI/` 会盖住新版界面"。这轮问另一半：**旧版本在更新目录里留下的状态文件，新版会不会继承？**

`<配置目录>/updates/apply-state.json` 是替换脚本写出的结果记录（`applied` / `replace_failed` /
`backup_failed` / `verify_failed` + 版本 + 时间），由**下一次启动**读出来回给界面。
它**跨版本**留在同一路径上，而**除了下一次替换**，没有任何地方会清除或忽略它。

## 2. 实测（真实产物，portable 实例）

在一份从快照发布的单文件 EXE 上（`portable.flag` + `data/updates/apply-state.json`），分别放入两种陈旧记录，
启动后取 `GET /api/update`（需要会话令牌，取自页面里的 `pineglow-session-token`）：

| 放进去的陈旧记录 | 接口实测返回 |
| --- | --- |
| `{"result":"replace_failed","version":"1.0.0",…}` | `lastApplyResult = {"result":"replace_failed","applied":false,"version":"1.0.0","writtenAtUtc":"2026-08-10T10:00:00+00:00"}` |
| `{"result":"applied","version":"1.0.0",…}` | `lastApplyResult = {"result":"applied","applied":true,"version":"1.0.0",…}` |

即：**接口原样回传**（`LocalApiService` 第 4733–4750 行，没有与 `currentVersion` 做任何比较）。

界面侧的代码路径（`ui/js/launcher.js:3809`）：

```js
const last = s.lastApplyResult;
if (last && last.applied === false) { … ⚠️ 上次替换失败 … · <version> … }
```

⇒ **只有 `applied === false` 才会渲染警告横幅**；`applied === true` 不显示。所以症状被限制为：

> 用户在旧版本上经历过一次**失败的替换**（例如无权限导致 `replace_failed`），
> 之后用别的方式升级到新版——设置页会**一直**显示"上次替换失败 … · 1.0.0"，
> 而当前版本其实是好的、也没人再去尝试替换。直到下一次真正执行替换才会被覆盖。

## 3. 严重性与边界（不夸大）

- **不是功能故障**：不影响启动、检查更新、下载或替换本身，属"陈旧提示"类问题。
- **触发条件较窄**：需要旧版本留下**失败**记录（成功记录不显示；而第 25 轮那种 `timeout` 卡死
  根本走不到写状态那一步 ⇒ 不产生记录）。
- **实测的局限（如实说）**：本次验证里记录里的版本与运行版本**都是 1.0.0**（因为当前构建就是 1.0.0），
  所以"版本不一致时会不会显示"我并没有单独跑出来；我说的是
  **接口与界面两处代码都没有做版本比较**（这点在代码里可直接看到），加上接口原样回传已实测。
- 未验证清洗策略的副作用（例如"只在版本匹配时才显示"会不会反而掩盖真实失败）。

| 处置 | 代价 |

## 5. 顺带记录：一句代码注释与真实优先级不符（第 25 轮隐患的另一面）

`ResolveUiRoot()` 第 242–244 行的注释写着：把内嵌解包**放在 `configDir/UI` 之前**，
"是为了保证用的是**当前 EXE 自带**的界面，而不是历史版本留下的目录"。
这句话对 `configDir/UI` 成立，但**EXE 旁的 `UI/`（第 236 行）仍然排在解包之前** ——
也就是第 25 轮实测到的升级隐患。需要说明的是：这个优先级**很可能是为了开发树便利**（跑 `dotnet build`
时用活的 `ui/` 而不是嵌入快照），属有意为之；但**注释给出的理由与整体优先级并不一致**，
容易被下一个人读成"已经保证用自带界面了"。已在复评的决策项里与隐患 A 一并列出。
