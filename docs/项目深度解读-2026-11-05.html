01 一句话结论

先给判断，后面全部是证据。

这是一个功能完整度远超个人项目平均水平、安全与交付纪律近乎偏执，但架构复杂度已经明显超出其文档治理能力的 Windows 原生启动器。

它的核心不是 UI，也不是 Minecraft 协议，而是一个把 Web 前端当作「远程客户端」来对待的本地 HTTP 服务。所有能力——启动游戏、装 Mod、二分定位崩溃、AI 诊断、自更新——都被收拢到 LocalApiService 这一个静态类里。这个决定带来了极快的迭代速度和极强的可测试性，也留下了项目最重的一笔债。

更值得注意的是它的开发方式：docs/ 里有 538 份 Markdown，大量是「执行提示词 → 工作流 → 独立验收 → 返工 → 复验」的成对记录，代码里到处是 MR04、R01、Phase 3B 这类返工编号的注释。项目是被 AI 辅助执行 + 人工独立验收反复雕出来的，因此「证据链完整」和「文档严重滞后」这两个特征同时存在。

安全边界

会话令牌、Origin 白名单、SSRF 精确域名白名单、路径重解析点钉住、凭据隔离、导出脱敏，都有代码与测试双重落地。

02 它是什么：定位与规模

GPL-3.0 开源，仓库 github.com/zhangtanze1359/Pineglow-Launcher，.NET 10 / Avalonia 12。

产品定位：对标 HMCL、PCL2、Prism Launcher、Modrinth App 的第三方 Minecraft 启动器。功能面已经很宽——离线 / 微软正版 / Authlib 外置登录；官方版本安装与 SHA1 校验、断点续传与可恢复任务；Forge / Fabric / NeoForge / Quilt / OptiFine；Modrinth / CurseForge 内容搜索与安装；实例隔离、实例级 Java；Mod 健康检查、依赖解析、二分定位；存档备份、服务器 Ping；皮肤 3D 预览（内嵌 Three.js）；崩溃规则分析 + OpenAI 兼容 AI 诊断；自更新与中英双语。

它的差异化不是功能数量，而是两件事：纯 Web UI 带来的前端迭代成本，以及「崩溃日志 → AI 解释 + 一键禁用嫌疑 Mod」这条闭环（roadmap 明确论证：竞品里 HMCL-AE 仍停留在试验阶段）。另外工程底子里的可逆性设计很突出——删 Mod 进恢复区、替换失败回滚、二分定位结束自动恢复、删除实例只删配置不删文件。

03 架构解剖：三层与一条数据总线

最常见的误读是把它当成「Avalonia 应用」。实际上 Avalonia 只负责画一个窗口和承载 WebView2。

为什么这个架构值得肯定

  • 前后端彻底解耦：改 ui/ 不需要重编 C#；file:// 直接打开 index.html 就是一套内存 mock 的完整可演示界面。这让 UI 验收可以脱离后端独立进行。
  • 业务逻辑只有一份：开发纪律明确写「前端禁止重复实现启动/下载逻辑」，前端只是「接通 + 渲染」。
  • API 天然可被测试驱动：HTTP 接口比 WebView 桥接好测得多，项目里有 VerifyHost --bisect-smoke 这种进程内起服务、自建 portable 沙盒、跑完自动清理的 API 级 E2E。

代价

  • 浏览器里跑的页面可以调用能启动任意 Java 进程、删改游戏文件的本地 API——所以会话令牌不是可选项而是生死线（见第 5 节）。
  • 静态类 + 全局可变状态承担了全部编排，LoadConfig() 里还有 GetAwaiter().GetResult() 的同步阻塞，并发下有锁竞争与线程池压力隐患。
  • 手工路由靠 seg.Length 逐段匹配，历史上真的出过事故：10 条路由因为被嵌在 seg.Length == 4 块内而恒假、永远 404（2026-10-03 才修复并补了静态断言测试）。

04 六个真正决定成败的机制

读懂这六处，就读懂了这个项目 80% 的设计取舍。

① 本地 API 的会话令牌闭环

进程启动时生成 RandomNumberGenerator.GetBytes(32) 的十六进制令牌，只存在内存里。ServeStaticAsync 返回 index.html 时，把其中的 __PINEGLOW_SESSION_TOKEN__ 占位符替换成真令牌；api.js 从 <meta name="pineglow-session-token"> 读出，注入每个 fetch 的 X-Pineglow-Token。除 /api/health 外所有接口都校验，用 CryptographicOperations.FixedTimeEquals 防时序侧信道。<img src> 无法带 header 的两个接口（皮肤图、内容图标）走等价的 token= 查询参数。

这解决了本地 HTTP 服务最经典的漏洞：任意网页 / DNS rebinding 通过 127.0.0.1:48123 暗中调用本机 API。配套的 IsAllowedOrigin 要求 Origin 必须是同端口的 loopback HTTP，否则 403。

② 单文件发行与 UiBundle 内容指纹

发布物是「一个 EXE，别的什么都不带」。这逼出了两处非平凡工程：

  • csproj 里 IncludeNativeLibrariesForSelfExtract=true——否则 SkiaSharp / HarfBuzz 原生库留在 publish 目录，单独拷 EXE 冷启动直接 DllNotFoundException 崩在 Skia 初始化（注释里记录了这次实测）。
  • UI 资源以 EmbeddedResource 嵌进程序集（发布时不再外置 UI/），由 UiBundle 按「版本 + 资源内容 SHA」解包到 data/UI/<key>，先写临时目录再整体改名。指纹的作用是防止「新后端 + 旧界面」：目录式旧安装原地换 EXE 时，残留的外置 UI/ 不会被复用。

11-03 冷启动证据里，解包目录是 1.0.1-5e83ae616088，并逐字节比对了「解包界面 == 候选源码」，同时断言冷启动目录里没有外置 UI/ 和原生 DLL、真实主窗口标题出现、/api/health 就绪。这是很硬的验收。

③ 三套异步任务状态机

重操作一律「入队即返回 + 后台跑 + 前端轮询」：DownloadTasks（装版本）、ContentTasks（装 Mod / 整合包 / 光影 / 资源包）、UpdateGate（自更新单任务）。分别用 DownloadGate / ContentGate / UpdateGate 分锁，进度通过加锁的 UpdateContentTask 更新。配置写入另有 ConfigGate + 原子替换 + .bak/.prev 保护。设计上干净，代价是状态全在静态字段里，进程重启后只能靠 ResumableTasks 这类落盘结构恢复。

④ 启动参数装配（最核心的一段业务逻辑）

LauncherService.BuildCommandAsync → 解析版本 JSON → BuildReplacements 生成占位符表 → ResolveJvmArguments / ResolveGameArguments → classpath（含 natives 与加载器 client jar 判定）→ Process.Start。

一处能说明项目性格的注释 代码里明确写着「不能对整张参数表去重」：现代 Forge / NeoForge 的版本 JSON 会重复 --add-opens / --add-exports token，去重会把第二个取值当成主类，JVM 立刻退出。11-03 那次重构把 goto 改成 if/else 后，专门写了差分探针：19 种 JSON 形态 × 5 种 legacy 参数 × 4 种窗口 × 5 种服务器 × 2 种账号 = 3,800 组输入 / 7,600 个结果，重构前后逐字节相同。这是「行为保持重构」的正确做法。

⑤ 数据持久化与凭据隔离

默认配置目录仍是历史遗留的 %APPDATA%\MCMiniLauncher（命名空间已统一为 Pineglow.Launcher.*，但用户数据路径没改，避免迁移风险）。AppConfig 里 Microsoft token / CurseForge Key / 代理密码标 [JsonIgnore] 不入盘，真值走 SecretStore：Windows 凭据管理器（目标名 MCMiniLauncher/{name}），非 Windows 降级 secrets.json。

SecretStore 自身也是一次安全返工的产物：修复前测试跑 5 个配置用例就会真实产生 20 次 delete-intent 打到用户凭据管理器。现在原生调用被抽成可注入的 ISecretStoreBackend，测试程序集在 [ModuleInitializer] 里换成内存后端（fail-safe），并用 ProductionBackendCallCount 证明「原生调用次数为 0」。

⑥ 前端竞态防护（被返工次数最多的地方）

没有框架、没有虚拟 DOM，10 个视图全靠模板字符串 innerHTML + 事件绑定。因此项目自己造了一套并发控制：navSeq 全局递增做导航代次，contentPageGen 单独处理资源页内交错，dataset.rendered 做懒渲染，_modalAborters 在切页时取消进行中的 AI 诊断请求，NEWS_REQ_GEN / dlReqGen 各自防陈旧响应。

goTo() 里那段注释把「为什么必须在写 DOM 之前再校验一次 navSeq」讲得很清楚：否则过期请求会先清空 innerHTML、打好 rendered 标记、绑完事件，才被短路返回——污染已经不可逆。这类注释在 launcher.js 里密度极高，是四轮独立验收（10-16 run01 到 10-17 run04）留下的痕迹。

06 质量体系与「独立验收」文化

这个项目最不寻常的地方：它把「不许悄悄少跑几个测试」做成了 CI 硬门槛。

  • R04 测试清单双向断言：scripts/test-inventory.txt 是唯一权威清单（29 条 node 测试 + 1 个 C# 项目）。起因是发现 build.yml 曾硬编码 11 个前端测试文件，而磁盘上有 21 个，漏掉的 10 个在 CI 里从未执行过。现在 run-inventory-tests.cjs --check 双向断言：清单里写的必须存在，磁盘上 *.test.cjs 必须都在清单里，少列、多出、被删都非零失败。
  • R02 UI 资源闭包：check-ui-resource-closure.cjs 校验 index.html 引用的资源全部存在，缺一个就拦下发布。
  • 发布门槛：release.yml 的 verify job 在 Windows 上跑资源闭包 → 清单一致性 → 380 项前端测试 → 957 项 C# 测试，全过才进入 release。build.yml 另做 win/linux/osx 三平台 RID 发布，Linux 上跑 xUnit 与前端测试，Windows 上跑 bisect 冒烟。
  • 独立验收证据包：docs 下按 run01/run02/run03/run04 分目录存着 CDP 探针脚本、日志、截图、exit code、SHA256 清单。文档里反复出现「本报告不构成实现或发布授权」「未启动真实 GUI，相关行为仍为未验证」「不能据此代替 GitHub 同版本通过」这类克制的边界声明。
但证据链并不等于全绿 11-03 发布候选的实际结果：node-tests.exitcode=0（380/380）、dotnet-tests.exitcode=0（957/957）、publish.exitcode=0、cold-start-outside.exitcode=0（工作区外冷启动 PASS），但 cold-start.exitcode=1——工作区内的冷启动因 HttpListener 失败。诊断文档如实记录了这一点，没有把它写成「已解决」。

09 技术债与风险清单

按「如果不处理，会先伤到什么」排序。

P0文档与代码的安全描述相反

api-reference / architecture 仍写「CORS * 全放开、无令牌」，代码已强制令牌 + Origin 白名单。任何按文档做的安全评审、集成或渗透测试都会得出错误结论。建议立刻修这两处，并把 docs 头部日期改成实际核对日。

P0发布阻塞根因未闭环

v1.0.1 两次 CI 失败于 JavaLocator 递归扫描（单次 125 秒），本地快照全绿不能替代 runner。诊断流程文档已写好 6 步并明确禁止「调高阈值 / 删测试 / 放宽工作流」这种假修复，但实施证据尚未出现。另有 Ubuntu Node 测试 goal-validation.test.cjs 进程未启动的独立失败待定位。

P0LocalApiService 5,816 行上帝类 + 手工路由

约 60 个端点、全部业务编排、静态文件服务、配置读写、三套任务状态机都挤在一个静态类里，靠 seg.Length is 5 or 6 or 8 这类条件区分。已经出过一次「10 条路由恒假」事故，静态断言只能防同类嵌套，防不了新增分支时的长度混淆。engineering.md 早在 8-16 就把「手工路由缺乏集中注册表」列为改进点，至今未动。

P1前端单文件与三套 CSS 叠加

launcher.js 249 KB / 4,500+ 行，10 个视图、所有弹窗、Markdown 渲染、AI/二分/新闻逻辑全在里面；figma.css → pineglow.css → redesign.css 三层按序覆盖，后者是 10-14 的暗色重设计并重新定义了同一批 token。design-system.md 统计 figma.css 有 50+ 处硬编码色值，违反项目自己定的 token 红线，且与 development-guide.md 的「一律走 figma.css token」要求互相打架。零构建是优点，但也意味着没有模块边界、没有 tree-shaking、没有类型检查。

P1「跨平台」名不副实

Win32 P/Invoke 硬编码在宿主层、WebView2 强依赖、无边框窗口逻辑无 Linux/macOS 分支。三平台 CI 只保证「能编译」，不保证「能跑」。README 与 roadmap 都如实标注了，但产品名与首页仍容易让人误解。

P1工作区改动与 v1.1.0 计划的隔离要求冲突

计划要求「从发布基线建立隔离分支，保留原工作区与历史证据」，但 10 个产品文件改动 + 6 个未跟踪条目仍堆在主工作区未提交。考虑到 10-10 那次误删事故和「未推送提交永久丢失」的教训，这批改动是当前最实际的资产风险。

P2测试覆盖的结构性缺口

开发指南明确「不写 GUI / WebView 集成测试，UI 靠 mock 模式人工验收」；bisect-smoke 曾在路由修复前长期失败而没人发现，文档也注明「尚未在真实 GitHub Actions 中运行，不能当作 CI 已覆盖」。1,337 项测试里绝大多数是纯逻辑与静态扫描，真实启动链路靠人工证据包补。

P2生态兼容硬缺口

缺 Cleanroom / Legacy Fabric（HMCL 已覆盖，MR15/16 明确记为未授权）；自定义 .mcm 实例格式不与 Modrinth .mrpack / Prism 互通；主题系统、共享实例协作、插件扩展均未做。roadmap 已按优先级列清，属于「知道但没做」，不是盲区。

P2大量验证项仍是 BLOCKED / NOT_RUN

多轮独立验收如实标注：真实微软账号、真实 AI Key、Gitee token、进入世界长时游玩、在线 NuGet 还原（LIMITED）、win-x64 RID 锁定还原（NU1004）、真实发版与替换重启均未跑通或未放行；10-13 默认在线九页 FAIL 6/9；公开报告还保留着 TOCTOU 竞态、默认皮肤 / favicon 404 等条目（当前工作区已补 favicon，但未见闭环证据）。这些「未验证」标签是项目可信度的一部分，不应被 1,337 项全绿的数字盖过去。
