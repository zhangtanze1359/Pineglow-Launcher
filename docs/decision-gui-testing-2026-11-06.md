# 决策记录：GUI / WebView 集成测试的取舍（2026-11-06）

> **性质**：书面决策，不是发现。它回答「为什么不做逐控件 GUI 回归」，以及「不做之后靠什么兜住」。
> **最后核对日：2026-11-06**（对照 `remediation/v1.1.0` HEAD `5bdebfa` 与补测后的 `481` 项前端测试实测）。
> **对应事项**：`rNmpJX`（M2-3）。

## 一、决策

**不建立逐控件 GUI 回归体系。** 保持现有「发版前人工逐页验收 + 数据契约自动化」的分工。

**风险接受人**：owner（当前唯一成员）。这一条不能省略——没有明确接受人的「风险接受」等于没有决策。

## 二、为什么不建

三条理由，按重要性排序。

### 2.1 变更频率与自动化成本恰好反向

10 个视图（home / installations / worlds / servers / content / skins / downloads / news / settings / playtime）的控件交互集在**百级**。而其中变更最频繁的部分是**文案与布局**：

| 变更类型 | 频率 | GUI 自动化收益 |
|---|---|---|
| 文案（i18n 键值） | 高 | **零** —— 控件还在原地，只是字变了，测试照样绿 |
| 布局 / 间距 | 中高 | **零** —— 选择器不变，位置变了，测试照样绿 |
| 控件新增/删除 | 中 | 高 |
| 校验逻辑、状态机 | 低 | 高（但**不需要 GUI**，见 2.2） |

也就是说：**GUI 自动化最擅长抓的那类回归，恰好是变更最少的**；而它完全抓不到的文案/布局回归，才是日常。这是投入产出倒挂，不是"时间不够"。

### 2.2 真正会坏的逻辑已经能在无 GUI 层测到

补测后（`test-baseline` 一节）前端测试从 385 → **481**，覆盖的分层是：

| 层 | 手段 | 抓什么 |
|---|---|---|
| 数据契约 | `api-live-contract.test.cjs`（47 项） | 每个 `SG.api` 方法的 method / 路径 / body 是否正确。**接口错了界面一定错**，而这类错误用 GUI 测反而更慢 |
| 纯函数 | `launcher-ui-pure.test.cjs`（20 项） | 转义、单位换算、零值判定（CV-05）、兜底 SVG |
| 状态机 | `prelaunch-guide` / `save-recovery-ui` / `news-behavior` / `update-monitor`（合计 60+ 项） | 拦截、重试、乐观更新、竞态丢弃 |
| 渲染内容 | `renderWorlds` / `renderSaveRecoveryList` 等的直测 | 空态、错误态、XSS 转义 |

GUI 层要补的是**最后那一跳**：真实 DOM 事件触发 → 真实 WebView2 渲染。而这一跳的失败模式（点错了、点不到）恰好是人工验收一分钟内能发现的。

### 2.3 零构建架构是项目的优点，不该为测试引入构建链

`ui/` 是**零 npm 依赖、`file://` 可直接打开**的纯静态资源。任何主流 GUI 自动化方案（Playwright / Cypress / WebdriverIO）都要引入 `node_modules` + 浏览器二进制（数百 MB）+ 一套配置。这与「单文件 EXE、内嵌 UI、离线可跑」的产品形态冲突，也与 `M1-3` 明确要求的「仍不引入构建工具」冲突。

## 三、不建之后靠什么兜住（补偿门槛）

决策必须有代价对冲，否则就是逃。三条补偿，**都是发版前强制项**：

### 3.1 `verify-ui-pages-live.cjs` —— 真实 WebView2 逐页验收

- 通过产品自带 CDP 端口连真实 WebView2，逐页**真实点击导航**（`.nav-item[data-nav]` 的 click）；
- 断言：容器存在、激活态正确、渲染出**非平凡文本**、逐页截图；
- 统计并断言 `exceptions=0`、`consoleErrors=0`、`productLocalFailures=0`、`uiAssetFailures=0`、`landedErrorStates=0`；
- **10 个视图**（`VIEWS` 数组，`playtime` 在列），隐藏图按真实渲染/布局判定（不依 `aria-hidden`）。

本轮实测：`views=10, okViews=10, externalPending=0, landedEmptyStates=3`。

**它覆盖的是「能渲染、不报错」，不覆盖「每个控件点下去行为正确」**——这个边界必须写清楚，不能拿它当 GUI 回归的替代品。

### 3.2 481 项前端测试 —— 覆盖「界面背后的判断」

即 2.2 那张表。它们的价值在于：**GUI 测不到的地方，它们能测**。典型例子是 `prelaunch-guide`：它验证「问题码 → 处理入口」的映射，而不是「按钮长什么样」——后者一变就废，前者才是真正的契约。

### 3.3 一个前置门槛：脚本加载清单的单一来源

`ui/tests/helpers/ui-script-order.cjs` + `ui-script-order.test.cjs`。它守的是 GUI 测试**天然守不到**的一件事：拆出去的视图脚本忘了登记进 `index.html` 时，生产环境那一页会白屏，而**所有测试都绿**。这条门槛让这种漂移立刻变红。

## 四、什么时候应该重新考虑

写清触发条件，避免这个决策变成永久借口：

1. **单人项目变成多人协作**，且出现「改 A 页坏了 B 页」的重复事故 ≥ 2 次；
2. 控件级缺陷在**发版后**被用户发现 ≥ 2 次（说明人工验收确实漏了）；
3. 出现真正的商业 SLA 要求（客户合同里写了可用性/回归承诺）。

任一条成立时重开此决策，届时再评估 Playwright 的引入成本——**那时引入构建链才有正当理由**。

## 五、如实记录的限制

| 限制 | 后果 |
|---|---|
| 无逐控件交互回归 | 控件级行为回归只能靠人工验收发现 |
| 人工验收依赖截图复核 | 复核人疲劳时会漏；本轮 10 张截图已人工复核过一次 |
| 仅 Windows 有真实 WebView2 | Linux/macOS 的渲染路径**从未被验证过**（与平台支持的既有口径一致：仅 Windows x64 正式支持） |
| `verify-ui-pages-live.cjs` 需要真实单文件 EXE | 不能在纯源码状态下跑，必须在构建产物上跑——所以它天然是发版前步骤，不是提交前步骤 |
