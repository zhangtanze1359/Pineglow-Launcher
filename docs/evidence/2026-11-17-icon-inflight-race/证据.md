## 二、根因

`ContentIconService.DedupedFetchAsync`（修复前）：

```csharp
task = FetchAndCacheAsync(...);
_inFlight[cacheKey] = task;
_ = task.ContinueWith(_ => { lock (_inFlightGate) { _inFlight.Remove(cacheKey); } }, TaskScheduler.Default);
```

问题在**赋值与注销之间的窗口**：

1. 用例注入的 fetcher 是 `Task.FromResult(...)` —— 整个下载链在没有真正的 await 让出点的
   情况下**同步跑完**，于是 `task.IsCompleted == true` 在它被写进 `_inFlight` 的那一刻就成立。
2. 注销被安排在 `TaskScheduler.Default` 上，需要另一个线程才有机会执行。
3. 测试线程紧接着发第二次 `GetAsync`：`_inFlight` 里还留着**已经失败**的旧任务，
   于是第二次请求拿到它、直接返回 `UpstreamError`，`fetchCount` 停在 1 —— 断言在第 606 行失败。

也就是说：**「重试」这个语义被一个清理延迟吃掉了**，而延迟长度取决于线程池调度，
所以是概率性的。

顺带记录一条同源的隐患：原清理回调不判"这条记录还是不是我"。
如果旧任务的注销回调在新任务写入同名 key 之后才跑，它会删掉**新**条目，
同键去重随之失效（同一图标并发下载两次）。本次一并处理。

---

## 三、修法

`dev/PineglowLauncher/Pineglow.Launcher.Services/ContentIconService.cs`：

1. **建任务后同步判断**：`task.IsCompleted` 为真就不进表、也不排注销。
2. **复用前也判**：`_inFlight` 命中时要求 `!existing.IsCompleted`，防止"注销还排在队列里"的旧条目被复用。
3. **注销改为按引用匹配**（`RemoveIfSame`）：只有表里存的仍是这个任务才删。
4. 注销回调改用 `TaskContinuationOptions.ExecuteSynchronously`，让它在任务完成线程上立刻跑，
   不再白白绕一趟线程池。
5. 新增 `internal int InFlightCountForTest`（只读、加锁），供测试观测这条不变量。

**没有降低任何断言的严格度**：`FailedFetchAllowsRetry` 的三条断言（第一次 UpstreamError、
第二次 Ok、fetcher 恰好 2 次）一字未改，只是**多**加了一条「失败后表里必须为空」。

## 四、测试

### 1. 加强既有用例（`GetAsync_FailedFetchAllowsRetry`）

在第一次 `GetAsync` 之后插入：

```csharp
Assert.Equal(0, svc.InFlightCountForTest);
```

这条断言直接钉住根因。语义是「已完成的条目不得留在表里」，不是「重试次数够多就行」。

### 2. 新增反向守卫（`GetAsync_InFlightEntrySurvives_UntilTheDownloadActuallyCompletes`）

用两个 `TaskCompletionSource` 精确控制悬挂点（不用 `Task.Delay` 充当"已进入关键路径"的证据）：

- 悬挂期间表里必须是 1；
- 悬挂期间第二次调用必须复用同一任务（`fetchCount` 全程 1）——保护去重不被"过度修复"破坏；
- 释放后两次调用都拿到 `Ok`；
- 完成后（给 5 秒上限轮询）表必须回到 0。

## 六、这次没做的

- 没有把 `_inFlight` 的清理改成 `ConcurrentDictionary` + 原子 `TryRemove`。现在的锁已经够了，
  换成并发容器只会把"谁删谁"的判断藏得更深，而这次真正需要的是**明确的不变量 + 能观测它**。
- 没有动 `AwaitWithCancellationAsync` 的取消语义（共享下载不归属调用者取消）。
  修的是"已完成条目滞留"，与取消无关。
