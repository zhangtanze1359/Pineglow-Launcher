## 一、问题

`LoggingAndPathsTests.LauncherLog_ManyConcurrentWrites_ProduceCompleteLines` 偶发失败：

```
Assert.Equal() Failure: Values differ
Expected: 200
Actual:   203
```

原始输出（未编辑）：`original-flake-observed.txt`（即 M1-3 第三步 C# 门槛首次全量的原文）。

实测频率：**10 次全量中 1 次**（首次复现 1 次 + 后续 9 次全绿）。
单独跑该测试 **3/3 通过**——说明它不是确定性缺陷。

---

## 二、根因

`LauncherLog` 是**进程级静态单例**（`dev/PineglowLauncher/Pineglow.Launcher.Services/LauncherLog.cs`）：
`_dir`、`_file`、`_writer`、`_lastDay` 全是 `static`，所有调用方共享同一个 `StreamWriter`。

该测试的流程是：

```csharp
LauncherLog.Init(dir);                                  // 把自己的临时目录设为"当前目录"
Parallel.For(0, 200, i => LauncherLog.Info("line-" + i));  // 写 200 行
string[] lines = ReadLinesWhileOpen(LauncherLog.GetCurrentLogFile());
Assert.Equal(200, lines.Length);                        // ← 断言"文件里恰好 200 行"
```

而 xUnit 默认**按 test collection 并行**（仓库无 `xunit.runner.json`，也无
`DisableTestParallelization` / `[CollectionBehavior]` 配置）。在本测试 `Init(dir)` 之后、
读回之前，任何**别的测试类**里触发的产品日志（`LocalApiService`、`ContentIconService`、
`UpdateService`、`UiBundle` 等都有 `LauncherLog.Info/Warn/Error` 调用点）都会追加进
**同一个** `_writer` —— 那 3 行就是这么来的。

### 为什么不能用 xUnit collection 修

`[CollectionDefinition(name, DisableParallelization = true)]` 的语义是**在同一个 collection 内**
串行。它无法阻止**未纳入该 collection** 的测试类并行运行。要真正隔离，必须把所有可能
触发日志写入的测试类全部塞进同一个 collection——本项目 90 个测试文件里绝大多数都可能触发，
这就等于全局关闭并行。

而 `LocalApiServiceTestCollection.cs:23` 明文写着：

> 不允许把整个测试程序集（assembly-level）关并行来掩盖资源归属；本 collection
> 仅对共享 LocalApiService 的测试类做资源互斥。

所以 collection 路线在本仓库是被明确禁止的。

### 为什么不能"另开句柄写外部行"来模拟

`LauncherLog` 的 `StreamWriter` 以默认共享模式（`FileShare.None`）打开日志文件，任何外部
`FileStream` 都打不开它（实测抛 `IOException: 文件被另一进程使用`）。这反过来说明：
**真实的跨类污染只可能通过 `LauncherLog` 自身发生**，不可能来自外部句柄。

---

## 三、修法（两步）

### 1. 修正判定口径（不是放宽阈值）

原口径「文件总行数恰好 200」把**与并发写无关的外部行**算成失败——这是口径错误，不是实现缺陷。
`Gate` 锁本身工作正常：200 条完整、不截断、不交错。

改为断言**本测试写的那 200 条**：

```csharp
var mine = lines.Where(l => l.Contains("[INFO] line-", StringComparison.Ordinal)).ToArray();
Assert.Equal(200, mine.Length);                                    // 一条不少
Assert.All(mine, l => Assert.Matches(@"^\[INFO\] line-\d+$", ...)); // 每条都是完整行（不交错）
Assert.Equal(Enumerable.Range(0, 200).ToArray(), indexes.OrderBy(x => x).ToArray()); // 0..199 各一次
```

**没有放宽任何一条断言**：条数、行格式、集合完整性（0..199 各出现且仅一次）都仍然硬断言，
只是不再把外部行算进来。

### 2. 补一条防回归测试

新增 `LauncherLog_ForeignLinesInSameFile_DontBreakConcurrentWriteAssertion`：

- 先写 200 条本测试的行；
- 再**通过 `LauncherLog` 自身**写 3 条外部行（确定性复现污染条件，不依赖运气）；
- 断言文件总行数 **> 200**（证明污染条件真的成立，前提失效时直接红）；
- 再断言本测试那 200 条一条不少、不交错、0..199 完整；
- 并断言外部 3 条一条没丢（`Gate` 锁不能吞掉同行写入者的内容）。

若有人把口径改回「文件总行数恰好 N」，这条测试立刻红。

## 四、验证

### 变异验证：防回归测试真的能咬住

把防回归测试的 `Assert.Equal(200, mine.Length)` 改回 `Assert.Equal(200, lines.Length)`
（保持可编译，只改变判定语义）：

```
Assert.Equal() Failure: Values differ
Expected: 200
Actual:   203
失败!  - 失败: 1，通过: 0，已跳过: 0，总计: 1
```

**精确复现了生产上的那次 203 失败**，随后还原。
原始输出：`mutation-B2-reproduces-203.txt`。

> 附带记录一次无效的变异尝试：最初只替换了断言文本、没保留 `mine` 定义，
> 结果是编译错误（CS0103）而非断言失败——那不是有效验证，已作废并重做为可编译版本。
> 另有一次「把并发测试口径退回旧写法」的变异在**无污染的干净环境**下仍然是绿的——
> 这恰好说明该口径只在存在污染时才有区分度，因此**不能**用它来证明守卫；真正承担守卫
> 职责的是防回归测试的场景化复现。
