## ⚠️ 最重要的发现：旧 Key 没有失效

按常理，`Regenerate` 应该让旧 Key 立即失效。**实测不是：**

```text
第 1 次:  新 Key=200   旧 Key=200
第 2 次:  新 Key=200   旧 Key=200
第 3 次:  新 Key=200   旧 Key=200
```

**两把 Key 同时有效。**

这意味着：

- **新 Key 就位** ✅（新版本会用上它）
- **旧 Key 仍可用** ❌（泄露风险**没有消除**）

`Regenerate` 在 CurseForge 的行为是**增加**而非**替换**。

## 要真正让旧 Key 失效

需要到 `console.curseforge.com` 的 API Keys 页面，**单独删除那一行**——
而不是用 `Regenerate`。

但截图显示该页面**只有一个 Key 行**（标着「张垚泽」）。这说明：

- 要么后台只维护「当前一把」，Regenerate 后旧值应当失效（但实测没有）
- 要么旧 Key 属于**另一个 Application**，不在这个页面上

**需要编排方到 CurseForge 后台核实这件事。**

## 过程中的三个异常（如实记录）

1. **前两次卡片收到的 Key 调用 API 返回 403，第三次同样的 Key 却返回 200。**
   三次拿到的值**完全相同**（`$2a$10$5Ae.h…Ol2Odz1e`）。
   说明不是"复制拿错"，而是 **CurseForge 侧有传播延迟**（或缓存未刷新）。
   **教训**：新 Key 生成后立即测试会得到假阴性，应等待并重测。

2. **`Regenerate` 按预期应使旧值失效，实测没有。**

3. **页面上的「复制」按钮可能没生效** —— 前两次通过它复制的值，与第三次手动拖选得到的**完全相同**，
   所以这个怀疑被排除；真正原因是第 1 条的传播延迟。

## 安全处置

- Key 全程只经**私密卡片 → 临时文件**，未进入对话正文、未进入仓库、未进入日志。
- 走 `gh secret set < 文件`，**不经 shell 变量**（`$2a$10$` 会被展开破坏）。
- 构建时用 `Get-Content -Raw` 读入环境变量，不用命令行参数。
