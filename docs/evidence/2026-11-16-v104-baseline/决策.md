## 二、三种走法（D0）

| 方案 | 做法 | 发布内容 | 代价 / 风险 |
|---|---|---|---|
| **A（调研原意）** | 从 `v1.0.3`(`30f7b56`) 开 `release/v1.0.4`，只挑「MCBBS / 登录文案 / 版本」三项 | 只含三项 + v1.0.3 全部内容 | 与本地 `main`（81 提交领先）继续分叉；v1.1.0 合流时要再解一次冲突 |
| **B（直接打 main）** | 当前 `69c947c` 打 `v1.0.4` | **整个 v1.1.0 线**（D3 自动备份、Mod 批量更新、C# 1410 测试） | 不是小步发布；81 个未推送提交 + 7 个未合并提交一起背上台；一旦出问题回滚面是整个 v1.1.0 |
| **C（混合，计划建议）** | 从 `v1.0.3` 切 `release/v1.0.4` 先发三项；`main` 继续留在 `69c947c` 作 v1.1.0 主线，v1.1.0 发布时再把这三项合回主线 | 同 A | 要并行维护两条线；但三项改动很小（7 个文件 + 1 条测试 + 1 条文案 + 版本/日志），合并成本可控 |

**我的建议：C。** 理由：
- 发布语义干净（用户装到的第一版 = v1.0.3 + 三项，而不是"突然多了整套 v1.1.0"）；
- 三条线的关系变成"主线 `main` 继续跑 v1.1.0，发布线 `release/v1.0.4` 只出一个 hotfix"，符合调研「PR #1 留给 v1.1.0」的本意；
- 三项改动足够小，将来把 `release/v1.0.4` 合回 `main` 时冲突面只在 7 个文件内，可枚举。

**A 与 C 的实际差别只有一件**：A 不打算把三项合回主线（v1.1.0 发布时不带这三项），C 会合回去。
考虑到 MCBBS 已失效、文案有误导，这两项**迟早必须进主线**，所以 A 会制造"同一个修复要做两次"的隐患。
