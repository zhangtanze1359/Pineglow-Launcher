# D3③ 真机 UI 验收（2026-11-16）

- 被测 HEAD：`7930c29`（`integration/v1.1.0-20261107`）
- 宿主：`dotnet build dev/PineglowLauncher -c Release -o …` 产出的 `Pineglow.Launcher.exe`，真实 WebView2 窗口
- 驱动方式：`PINEGLOW_WEBVIEW_DEBUG=9333` 打开 WebView2 远程调试端口，用 CDP
  （`Runtime.evaluate` 真实点击 + `Page.captureScreenshot`）驱动，**没有用 mock UI、也没有改产品代码**
- 隔离：构建产物目录放 `portable.flag`（`PlatformPaths.IsPortableMode`）→ 配置落在 `<app>/data/`，
  **完全不碰用户 `%APPDATA%\MCMiniLauncher\config.json`**

**结论：整条链路在真机上跑通——检查更新 → 全部更新 → 撤销，全程零异常。**

## 一、夹具

| 项 | 值 |
|---|---|

夹具设计的两个要点：
1. **无元数据的 Mod 必须有**（modB/modC）——用来验证"不会对它们发请求"；
2. **旧版本 ID 用伪造值**——这样"最新版 ≠ 已装版"必然成立，测试不依赖 Sodium 当前发到哪一版。

## 二、逐步结果（原始返回值）

| # | 动作 | 观察 |
|---|---|---|
| 1 | 打开「安装管理」→ 点实例卡片上的「Mod」 | 抽屉打开 |
| 2 | 抽屉工具条 | `#modCheckUpdates` 存在，文案 **检查更新**；`#modUpdateAll` 与 `#modUndoUpdates` 均为 hidden |
| 3 | 点「检查更新」 | 状态行 → **有 1 个 Mod 可更新**；`#modUpdateAll` 变为可见，文案 **全部更新（1）** |
| 4 | 点「全部更新（1）」 | 状态行轮询 → 结束为 **更新完成，已应用 1 个** |
| 5 | 更新后看 Mod 列表 | `Sodium 0.5.8+mc1.20.4 · 926.84 KB \| modB-1.0.0.jar · 17 B \| modC-1.0.0.jar · 17 B` —— **真实 jar 被下载并替换，版本号与大小都变了** |
| 6 | 「撤销本次更新」可见性 | `true` |
| 7 | 点撤销 | 状态行 → **已撤销 1 个** |
| 8 | 撤销后看 Mod 列表 | `modA-1.0.0.jar · 17 B \| modB-1.0.0.jar · 17 B \| modC-1.0.0.jar · 17 B` |

**零异常**：全程 `Runtime.exceptionThrown` 与 `Log.entryAdded(level=error)` 均为空。

## 五、这次覆盖了什么 / 没覆盖什么

**已覆盖（真机）**：检查更新（候选数量正确、无元数据 Mod 不发请求）、全部更新（真实下载+替换+版本号变化）、撤销（文件与侧车都回到旧值）、错误横幅缺失（零异常）。

**未覆盖（说清楚，不冒充）**：
1. **撤销冲突**：UI 上没有制造"目标被外部改过"的场景，这一条只有在单测里验过
   （`BatchUpdateTests.Undo_TargetModifiedExternally_IsRefused`）。没在真机点是因为需要在更新与撤销之间手工改文件，无法在同一个 CDP 脚本里稳定编排。
2. **取消**：后端有 `cancel` 端点，**前端没有取消按钮**——这是本轮就存在的产品缺口，不是验收遗漏。
3. **失败停止**：未构造"第 2 项失败"的真实场景（需要两个候选，一个故意给坏 sha1）。
4. 本夹具用的是 **Sodium 一个真实项目**；200 Mod 的实际耗时未测（并发上限 6 只保证不串行，不保证快）。
