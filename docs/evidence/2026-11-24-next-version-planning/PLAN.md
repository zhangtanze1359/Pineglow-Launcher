建议下一版定为 **v1.0.7（维护版）**。v1.0.6 已交付存档可恢复删除、退出后备份、Mod 批量更新与撤销、启动前检查。v1.0.7 优先保护存档的完整副本，让已有备份在失败时可重试，纠正 CurseForge 凭据行为与发布说明的差异，并补上测试夹具和实包升级的证据。失败提示与重试属于已有备份开关的可靠性补齐。主题工作室、可恢复的跨重启批次和逐项批处理交互保留给独立的功能版规划。

### 实施卡的关键约束

- **S1** 建议分清复制前、完整副本落盘、原目录退出活动位置、清理和恢复终态。跨卷先在目标卷暂存并校验，持久化可追踪状态后，再尝试把源目录同卷改名到活动存档列表之外。改名失败则保留源并报告占用等实际原因。清理前对账暂存源与已验证副本，发现写入变化就同时保留并报告状态。清理或状态写入失败时保留已验证副本。跨卷恢复先把完整目标发布到 `saves` 后再清隔离副本，中断重启后能重新对账。同卷回滚失败也保留可定位副本。API/界面对仍需恢复的完整副本提供可执行恢复路径，并阻止误导性的永久清理入口。现有 `ManifestSha256` 是文件相对路径和长度的摘要，保留旧记录兼容，逐文件字节哈希用于验收，跨卷发布前用能发现等长内容不一致的校验。[目录指纹实现](../dev/PineglowLauncher/Pineglow.Launcher.Services/SaveRecoveryService.cs#L391) · [恢复区 UI](../ui/js/launcher.js#L1682)
- **S2** 优先实现失败、部分失败、超时可见且抑制自动关窗，沿用 20 秒作为提示阈值。复用退出后备份和归档机制，以实际存档目录作为同宿主协调键，避免共用目录的两个实例同时写备份。共享实例仍运行时安全推迟或提示重试。归档发布须使用互不冲突的临时名和最终名，失败后仅清理本任务的临时文件。保留有效 ZIP，重试有明确状态，旧工作未结束时不启动重叠任务。
- **U1** 本轮收紧夹具，并做进程层可控的挂起与退出测试，保留每个已有业务断言。Windows 专用分支务必实际运行，非 Windows 走可断言的实际平台行为，并在证据中单列 `.bat` 覆盖。ACE 用例的前置准备失败须显式失败并输出诊断。先保证可独立复跑和记录并发度，若夹具共享环境需要隔离，使用有范围的非并行集合，另用显式负载保留竞争场景。生产脚本到达 300 轮上限后进入替换是现有产品策略，只有发现旧包回滚或文件完整性失败才另提产品修复。[脚本等待上限](../dev/PineglowLauncher/Pineglow.Launcher.Services/UpdateService.cs#L639)
- **R1** 用公开发布包的官方文件名，各建独立 `portable.flag` 案例，同一时刻只启一个宿主。准备合成实例、配置哨兵字段和存档，验证旧包开机版本。优先抓旧链默认源的选中清单与 `latestVersion=1.0.6`，若已变为 1.0.7，独立验证 `1.0.5 → 1.0.7` 直升。要回补精确旧链，需要另获授权的隔离测试网络和合规 HTTPS 通路，用 **v1.0.6 官方 tag 固定清单**或其逐字节副本，并确保旧客户端其它源无法选中更高版本。产品允许配置额外 `updateUrl`，仍会并行比较内置源，重点记录最终选中的版本、URL 和哈希。没有合规隔离条件就保留缺口。v1.0.7 发布前可用已授权、正常可信 HTTPS 的候选清单完成同链预演。另做一条受控错误摘要，验证保留旧 EXE 与数据且能重试。正式源上线之后用冻结的 v1.0.6 起点再验证，报告与发布附件的真实对应关系。[清单链](../dev/PineglowLauncher/Pineglow.Launcher.Services/UpdateService.cs#L93) · [资产 HTTPS 校验](../dev/PineglowLauncher/Pineglow.Launcher.Services/UpdateService.cs#L339)

## 执行顺序

1. **第 0 批，冻结输入并准备环境。** 编排方确认 v1.0.7 范围和允许、只读、禁止路径。在 `D:/Projects/_worktrees/` 分配实施与独立复验的不同工作树，固定 HEAD、状态、diff、输入哈希。准备两块可写的测试卷、Windows 交互桌面、合法 CurseForge Key、旧发布包和真实 Mod 夹具。R1 的旧版正式升级可立即单独跑，避免最新清单切换后失去原路径。
2. **第 1 批，实施与定向回归。** S1、S2、U1、C1 可并行分析和独立实施。同一份 `ui/js/launcher.js`、语言资源或 `scripts/test-inventory.txt` 的写入由编排方串行纳入，避免两个分支独立刷新同一清单。S1、S2 各自先跑定向 RED 和 GREEN。并行准备 C2、L1 的真机夹具。G1 记录来源状态、T1 只读考古可随时做。
3. **第 2 批，冻结整合候选并独立复验。** 编排方把本批补丁组成候选，固定提交和构建输入。独立人员在另一隔离工作树重跑 S1、S2、U1、C1 的关键反例，并用同包补 C2、L1、R1 预演。C2 或 L1 暴露的真实回归先由编排方确认是否纳入最小修复，变更候选后对受影响项目重新验证。
4. **第 3 批，交付与审批。** 产品只交付 **win-x64 单文件自包含**，CI 三平台矩阵是构建与测试门槛。候选运行 `node scripts/gates.cjs`，四道门真实通过，测试与 `scripts/test-inventory.txt` 双向一致并存原始计数。获准刷新基线后执行 `node scripts/gates.cjs --baseline`。候选执行 `node scripts/check-release-consistency.cjs` 并核对 csproj 和 release notes，待授权创建 tag 再查 tag 指向、tag 内的说明与最终版本三方一致。脚本现有 exit 0 本身不能证明候选 tag 已创建且对齐。独立复验和批准后才进入目标分支。推送、tag、Release 需编排方单独授权。随后核对实际 CI 作业、公开附件大小和哈希、隔离冷启动与 R1 正式源升级，失败先记录证据并交编排方决策。
