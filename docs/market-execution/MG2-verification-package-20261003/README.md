## 一、一条命令跑完全部自动检查

本机只有 Windows PowerShell 5.1（没有 `pwsh`），所以：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify-mg2.ps1
```

它会：

1. 汇总四个包的 `manifest.json`；
2. **证据漂移检查**：把各包记录的 SHA256 与当前工作区逐一比对；
3. 重新跑 C# 与 Node 全量测试，与各包声称的数字对照。

本次实测输出（完整日志见 `verify-mg2-full.log`）：

```
一致=21  无法解释的漂移=2  被后续包覆盖的历史记录=7  文件缺失=0
已通过! - 失败: 0，通过: 718，已跳过: 0，总计: 718
ℹ tests 216   ℹ pass 216   ℹ fail 0
C# exit=0  Node exit=0
```

> **那 2 条"无法解释的漂移"不是失败，是复验过程自己造成的**：
> 一条是本包补登记复现性脚本导致清单文件自身变化；另一条是复验时发现 MR12 的并发用例
> 有**非线程安全的计数**（全量跑时丢过一次计数）并修掉。**产品代码没有因此改变。**
> 原因、影响与处置见 `drift-notes.md` —— 请务必先读它再看结论。
>
> 同一轮复验还修掉一处**既有偶发**：`ContentIconServiceTests` 用
> `49777 + (线程Id % 100)` 派生端口，线程池里 id 相差 100 的两个线程会撞同一个端口，
> 实测复现 `HttpListenerException: 另一个程序正在使用此文件`。已改为操作系统分配空闲端口。
> 该偶发在 MR09 那轮也出现过一次，当时只判为"时序相关"，本次拿到确定根因。

## 二、证据漂移检查怎么读

复验最容易踩的坑是"证据里的哈希早就过期了，没人发现"。本包的检查口径：

| 计数 | 含义 |
|---|---|
| **一致 21** | 每个路径**最后一次**被记录的哈希，与当前工作区**完全一致** |
| **无法解释的漂移 2** | `scripts/source-snapshot-inputs.txt`（本包补登记脚本）与 `dev/PineglowLauncher.Tests/CurseForgeRateLimitTests.cs`（复验时修掉非线程安全计数）——**均已解释**，见 `drift-notes.md` |
| **被后续包覆盖 7** | 早期包记录的哈希被更晚的包合法覆盖（例如 `LocalApiService.cs` 被 MR08→MR11 连续修改） |
| **文件缺失 0** | 记录过的文件都还在 |

**任何"无法解释的漂移"都必须逐条说明改了什么、属于哪个包，否则该证据不可用于复验。**
本包没有通过"改脚本让它不报"来消除漂移——那会让检查失去意义。

## 四、复验方必须独立判断的事（脚本做不到）

1. **实现是否真的满足验收**：脚本不读代码。请按 `verification-checklist.md` 逐条抽查，
   尤其注意"执行者报告里说的"与"代码里做的"是否一致。
2. **RED 是否真实**：本仓库有三个包（MR08/MR11/MR12）的 RED 基线是**保留了新类型签名、只还原行为**构造的
   （直接把文件删掉只会得到编译错误，证明不了行为）。每个包的 `deliverable.md` 都写明了构造方式，
   请判断这个口径是否可接受。
3. **真实环境行为**：真实 GUI / 真实游戏 / 真实网络在本仓库环境**无法覆盖**，
   各包 `deliverable.md` 的"明确未做与未验证"一节逐条列了。
