## 三、瓶颈与候选修复（**未实施**）

### 3.1 瓶颈

`DiagnosticLogSanitizer.SelectEvidence` 的当前顺序是**先对整段日志跑 13 条编译正则，再挑相关行**：

```csharp
string sanitized = Sanitize(input);          // ← 对整个 1.2 MB 跑 13 条正则
IEnumerable<string> relevant = sanitized.Split('\n')...
```

而真正被用到的只有 `maxCharacters`（调用方传 4000 字符）那一小段。**这就是 30 ms 的来源。**

### 3.2 候选修复（最小改动）

调换顺序：**先按相关性挑行，再只对选中的行脱敏**。

### 3.3 实测收益（同一台机、同一次测量流程）

| | p50 | p95 | max |
|---|---|---|---|
| 当前实现 | 30.240 | 55.220 | 58.164 |
| 候选实现（测量实验） | **6.123** | **22.908** | 29.864 |
| 变化 | **−80%** | **−59%** | −49% |

> 候选实现**只存在于测量夹具里**（`LauncherPerfMeasurementTests.SelectEvidenceCandidate`），
> **没有进入产品代码** —— 卡片要求瓶颈修复走"独立精确子包授权"。

### 3.4 变化风险（必须随修复一起评估）

两者的差异不只是性能：

1. **判相关性的输入不同**：产品实现按**脱敏后**的文本判相关性；候选实现按**原始**文本判。
   当某行的关键词本身会被脱敏吃掉时（例如 `Authorization: Bearer Error123` → `[REDACTED_TOKEN]`），
   候选实现会把它当相关行选中、再脱敏成 `[REDACTED_TOKEN]`；产品实现则从一开始就不选它。
   → **选中的行集合可能略有不同**，需要人工比对若干真实日志确认可接受。
2. **截断语义不同**：产品实现在"整段脱敏后"按 `maxCharacters` 做头尾保留；
   候选实现先挑行再截断。截断点可能落在不同位置。
3. 因此该修复**不能只看性能数字就合入**，应作为一个独立小包，配套"同一批日志下选中行集合差异"的对比用例。

## 五、复验方法

```powershell
# 一键复现全部测量（约 3–5 分钟）
```
