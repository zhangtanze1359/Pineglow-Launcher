## 三、用户画像：**待验证假设**（不是结论）

以下画像**没有任何用户证据**，仅用于指导访谈取样。MR22 执行研究后必须逐条标注"被支持/被推翻/仍未知"。

| # | 假设画像 | 关键假设内容 | 若被推翻会怎样 |
|---|---|---|---|
| H1 | **HMCL 用户**（长期单实例） | 习惯手工放 Mod；出问题靠搜索引擎与日志文件 | 则"诊断历史/报告导出"（MR08）价值下降 |
| H2 | **PCL 用户**（多实例、重下载） | 关心下载速度与镜像源；对"更新失败"容忍度低 | 则 MR19/MR20 的更新链路优先级上升 |
| H3 | **Prism 用户**（多实例、重隔离） | 在意实例隔离与可回滚；愿意为可控性付出更多步骤 | 则 MR13（实例迁移）价值上升 |
| H4 | **整合包维护者** | 关心 `.mrpack` 兼容性、导出/分享、玩家反馈的可复现性 | 则 MR11 的规范校验与 MR08 的报告导出价值上升 |
| H5 | **新手**（首次装整合包） | 卡点在"下载慢/失败"与"缺前置 Mod"，而非"看不懂日志" | 则 AI 诊断（MR09）的实际价值可能低于预期 |
| H6 | **误删过 Mod 的用户** | 会尝试重新下载而不是找恢复入口 | 则 MR04/MR05 的恢复能力需要更强的可发现性（而非更多能力） |

**交叉假设**（同样未验证）：H7 "用户不愿外发日志"、H8 "用户不信任自动替换/自动禁用"。
这两条直接决定 MR08（外发授权）与 MR09（危险动作）的接受度，**必须在访谈中直接验证**。

## 四、与产品现状的对照（访谈脚本的依据）

任务脚本刻意只使用**已存在且已被验证**的流程，避免让受访者操作不存在的功能：

| 任务 | 依赖的产品能力 | 本会话中的验证状态 |
|---|---|---|
| 迁移一份已存在的实例 | `POST /api/instances/register`（挂回已存在的游戏目录） | 已实现（MR03 批次） |
| 首次安装整合包并进菜单 | `.mrpack` 导入（MR11） | 证据就绪；真实端到端**未验证** |
| 恢复一次 Mod 删除 | 恢复区（MR04）+ 替换撤销（MR05） | 证据就绪 |
| 定位预置崩溃 | Bisect（MR06/MR07） | 证据就绪；`--bisect-smoke` 全流程 PASS |

**注意**：卡片里的"迁移一个合成实例"**不是**产品功能——MR13（Prism/HMCL/PCL 实例迁移）是**条件包，未实现**。
因此任务 1 被设计为"观察用户**现在**怎么把已有实例接进来"，而不是"测试我们的迁移功能"。
