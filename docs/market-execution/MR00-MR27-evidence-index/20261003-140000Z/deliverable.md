## 八、复跑时发现并修掉的真实缺陷：`verify-mg2.ps1` 的漂移模型过弱

**自评时我发现索引 §一 引用的 MG1/MG2/MG3 数字是它们各自早先运行的结果**，而此后我在多轮里改过
白名单等文件 —— 那些数字可能已经变了。于是**四个脚本全部复跑**，结果证实了担心：

| 脚本 | 索引原先写的（旧） | 复跑实测（当前） |
|---|---|---|
| `verify-mg1.ps1` | 一致 42 / 漂移 0 | **一致 56 / 漂移 0** |
| `verify-mg2.ps1` | 一致 21 / 已解释 2 | **一致 17 / 无法解释 6** ⚠️ |
| `verify-mg3.ps1` | 一致 54 / 已解释 1 | **一致 56 / 漂移 1** |

### 6 条"无法解释"的根因不是实现，而是**脚本本身**

`verify-mg2.ps1` 旧实现只从 **MG2 自己的四个包**构建"最新记录"表：

```powershell
foreach ($entry in ($runDirs | Sort-Object Run)) { ... }   # ← 只有 MG2 的 4 个 run
```

而 `verify-mg0/mg1/mg3` 扫描**全部 run**。后果：某文件**后来被更晚的包改过**时，
MG2 看不到那条更晚的记录，于是把它报成"无法解释的漂移"。实测 6 条**全部**属于此类：

| 文件 | 记录来自 | 后来被谁改 |
|---|---|---|
| `ui/js/api.js` | MR11 | MR20（`trustNote`/`lastApplyResult` 归一） |
| `ui/js/i18n.js` | MR11 | MR17（无障碍键）、MR20（4 个键） |
| `ui/js/launcher.js` | MR11 | MR17（弹窗键盘契约）、MR20 |
| `LocalApiService.cs` | MR11 | MR03b（运行中守卫） |
| `scripts/source-snapshot-inputs.txt` | MR12 | MR17 / MR21 / MR24（白名单登记） |
| `CurseForgeRateLimitTests.cs` | MR12 | 已在 MG2 的 `drift-notes.md` 里解释过 |

**修正后**：`一致=249  无法解释的漂移=1  被后续包覆盖=78  缺失=0`
—— 只剩 `CurseForgeRateLimitTests.cs` 那一条，**MG2 自己的 `drift-notes.md` 早已解释**。

### 为什么值得修

修正前，任何复验方跑 MG2 都会看到 **6 条"无法解释的漂移"**，并被迫手工逐条排查——
其中没有一条是实现问题。**这是"证据看起来有问题"与"证据真有问题"的差别**，
而它直接决定 MG2 的证据能否被用于复验。

**修正前的数字（一致 17 / 漂移 6）保留在 MG2 自己的复验包里**，没有改写历史。
