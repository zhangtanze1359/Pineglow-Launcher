# MR19 补测 · win-x64 单文件自包含 exe 的逐字节可复现性

- **run-id**：`20261003-150000Z`
- **性质**：**关掉 MR19 明确留下的具名缺口**（不需要新授权：属"可复现构建"范围内的本机实验）
- **依据**：`MR19-reproducible-build-rid/20261003-070000Z/deliverable.md` §六：
  "**单文件自包含 exe 的可复现性** | 未测。托管程序集已实测可复现；自包含单文件包含 ILC/原生输出，需要单独研究"
- **最终状态**：**证据就绪（在本机同路径下）** —— 结果为正，但**跨路径/跨机器仍未测**（见 §四）

---

## 一、结论

> **两次完全独立的 win-x64 单文件自包含发布，产物逐字节一致。**

| 项 | 第 1 次 | 第 2 次 |
|---|---|---|
| 命令 | `dotnet publish -c Release -r win-x64 --self-contained /p:PublishSingleFile=true` | 同 |
| 发布前 | **整体删除 `bin/` 与 `obj/`** | **整体删除 `bin/` 与 `obj/`** |
| exit | 0 | 0 |
| 用时 | 9 s | 5 s |
| 文件数 | 18 | 18 |
| 单文件 exe | **89,490,941 bytes** | **89,490,941 bytes** |
| exe SHA256 | `C99101C8672D7861B6FEF2F29E20F144350771DD9E92F1ABB4DD8987BBA0EC13` | **同一值** |

**逐字节比对**：exe 一致 = **True**；文件清单差异 = **0**；内容不同的文件 = **0 / 18**。

**这不是"增量 vs 全量"的比较**：两次之间把该项目的 `bin/` 与 `obj/` **整个删掉**了
（脚本会打印解析后的绝对路径并校验它在项目目录内才删），因此第二次没有复用任何第一次的中间产物。

---

## 二、复跑方法

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\measure-singlefile-repro.ps1
```

脚本会：记录锁文件基线 → 两次（删 bin/obj → publish → 记录产物清单与逐文件 SHA256）→ 逐字节比对
→ 若不同则**定位首个不同字节并打印十六进制上下文**（用于判断差异像不像时间戳/路径）
→ 守住锁文件副作用 → 打印只含实测的结论。产物默认保留在系统临时目录供人工复核。

## 三、必须守住的副作用（脚本已自动处理）

RID 发布会把 `Microsoft.NET.ILLink.Tasks` 注入**共享的 `net10.0` 段**，从而**改写 `packages.lock.json`**：

| 时点 | 大小 | SHA256 |
|---|---|---|
| 开始 | 8663 bytes | `FBBC9AE6…EE0672` |
| 两次发布后 | **10868 bytes** | （已被注入 RID 段） |
| **自动恢复后** | **8663 bytes** | `FBBC9AE6…EE0672`（与开始**完全一致**） |

恢复来源：MR19 证据里的提交态副本 `red/launcher-packages.lock.json.before`。

**恢复后复核**（本包实跑）：

| 检查 | 结果 |
|---|---|
| `dotnet test --filter BuildLockFileTests`（不变量守卫） | **3 通过 / 0 失败** |
| `dotnet test`（全量） | **755 通过 / 0 失败** |
| `node --test`（18 个文件） | **230 通过 / 0 失败** |

> 这条副作用本身就是 MR19 §2.1/§2.2 的结论：**RID 发布与非 RID 锁定还原互斥**，
> 所以每次做 RID 发布实验都必须把锁文件还原并复核守卫。本包照做了，且留了哈希证据。

## 四、明确未验证（不要把上面的结果扩大）

| 项 | 说明 |
|---|---|
| 🔴 **跨路径** | **未测**。两次发布都在**同一路径** `D:\松光启动器` 下。单文件自包含的经典风险正是**嵌入路径**——换一个目录（例如 `C:\build\...`）再发一次才是否定/肯定这一点的证据。 |
| 🔴 **跨机器 / 跨 SDK** | **未测**。同机、同 SDK（10.0.301）。 |
| 🔴 **跨天** | **未测**。两次发布相隔约 4 秒且在同一天。若构建嵌入了**日期粒度**的时间戳，本次实验**看不出**；秒粒度的时间戳若存在则会暴露（结果一致，故不存在秒粒度时间戳）。 |
| **ILC/原生输出的确定性机制** | 未研究。本包只给"是否逐字节一致"的实测，**不解释**为何一致（不推测）。 |
| **真实 GitHub Actions 上的发布** | 仍未验证（MR19 §六 已列）。 |

**如果要彻底关掉"路径"这一项**，做法是：把工作区复制到另一个**不同长度**的路径下，再跑一次本脚本，
比较 exe SHA 是否仍相同。这需要一次额外的构建（约 10 s）与一份工作区副本，**本包未做**。

## 八、补记（第 27 轮）：跨路径已测 —— **结果是否定的**

本报告 §四 把"**跨路径**"列为未测。第 27 轮用 `scripts/measure-singlefile-pathcheck.ps1` **测了**：

**同一份源码在三个不同长度的路径下发布 → 三个不同的 exe SHA**（大小都是 89,490,941 bytes）：

| 构建路径 | 长度 | exe SHA256 |
|---|---|---|
| `D:\松光启动器` | 8 | `C99101C8672D7861B6FEF2F29E20F144350771DD9E92F1ABB4DD8987BBA0EC13` |
| `%TEMP%\pgA` | 45 | `3AFE016BBB80B5A686056DAD95A04A4BAE4B4EE7ED4859C3D2213300163B62F5` |
| `%TEMP%\pg-long-path-check-0123…` | 93 | `F1C10F08670C7D0FC9FAE0C4A612F1E49450F021FE7FD20507FC2474B92DA002` |

差异仅 **0.0019%** 的字节（1,691–1,725 个），首个不同偏移 **428（0x1AC）**。

**决定性对比**：排除 `bin/obj` 后，两个快照的 **256 个源码输入完全相同**（输入清单哈希均为 `4B73958C…`），
14 个差异文件全在 `bin/obj` 下、另 1 个独有文件是**文件名带路径哈希**的中间产物。
即：**唯一变量就是路径**。

**因此本报告 §一 的"逐字节一致"只在"同一路径"下成立。**
"单文件自包含 exe 可复现"**不得**不加限定地使用；应写"**同路径可复现、跨路径不可复现（实测）**"。

**机制未确定**（PE 时间戳 / bundle 清单 / approot 路径都是候选，本包未验证任何一条）。

详见 `docs/market-execution/MR19-singlefile-pathcheck/20261003-160000Z/deliverable.md`。
