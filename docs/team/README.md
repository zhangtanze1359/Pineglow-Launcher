# 松光启动器 · 开发团队编制

> 本目录是**一张编制表 + 接单规则**，不是新流程。
> 真正的规矩仍以 `AGENTS.md` 为准；这里只是把"谁做、谁不许做、交什么"写成可交接的卡片，
> 免得每轮重新口头分配一遍。

## 一、六个角色

| 角色 | 代号 | 一句话职责 | 默认执行者 | 主交付物 |
|---|---|---|---|---|
| **编排** | `ORC` | 拆任务、定依赖、判「现在能不能开工」、出决策材料 | 主会话 / Codex | `docs/handoff/派工总表-*.md`、决策材料 |
| **调研** | `RES` | 找外部事实，标注来源与**采样时点** | 任意带搜索能力的 agent | 事实清单 + 与本地实测的差异表 |
| **设计** | `DES` | 界面、交互、设计系统一致性 | Opendesign / Claude Code | 设计说明 + token 对照表 + 前后截图 |
| **开发** | `DEV` | 实现 + 自测 + 提交 | DSH / Codex / Claude Code | 代码提交 + 自测输出 |
| **审查** | `REV` | **重跑命令**后独立判定 | 必须是**没参与执行**的人 | `docs/evidence/<日期>-<轮次>/验收报告.md` |
| **台账** | `LED` | 状态回填、证据巡检、清单双向断言 | WorkBuddy / Hermes | 台账更新 + 巡检结论 |

角色卡在 `roles/`，一件事一张卡。**先看卡，再看任务。**

## 二、两种用法，别混

### A. 真并行（同一个会话里铺开）

主会话可以按 pi 的 subagent 角色代跑，映射是固定的：

| 团队角色 | pi subagent 角色 | 能写文件 |
|---|---|---|
| `RES` 调研 | `scout` | 否 |
| `ORC` 编排 | `planner` | 否 |
| `DES` 设计 | `worker` | 是 |
| `DEV` 开发 | `worker` | 是 |
| `REV` 审查 | `reviewer` | 否 |
| `LED` 台账 | `worker` | 是 |

并行铺开时，每条支线必须**改不同的文件**，否则冲突成本比收益高。
`REV` 不许和执行者同一个子任务里跑——那样等于自己给自己签字。

### B. 交接（写给下一个 agent 的工单）

用 `派工模板.md` 生成 `docs/handoff/HANDOFF-<日期>-<角色>.md`，格式照
`docs/handoff/HANDOFF-2026-11-07-claude-code.md`（已验证可用）。
关键在**路径边界**那一段：允许写哪些目录、只读哪些、禁止哪些，写死。

## 三、工作流与失败回退

```
RES 出事实 ──→ ORC 拆单定依赖 ──→ ┌─ DES ┐
                                  ├─ DEV ┤──→ REV 重跑验收 ──→ LED 回填台账
                                  └─────┘         │
                                                  └─ 红了 → 回 ORC 重排，不是回 DEV 硬修
```

三条回退规则：

1. **REV 判红 → 回 ORC**。让开发自己去改红项，等于让被告当法官；ORC 要判断是"实现错"还是"验收标准写错了"。
2. **依赖没成立就开工 → 作废**。历史教训：`C1`（基线判定）还没结论就开 `D1`（合流），等于把分叉问题丢给最忙的人临场判断。
3. **证据缺失 → 按未完成算**。不许用"我知道跑过了"补位。

## 四、铁律（`AGENTS.md` 硬约束的提醒，不替代原文）

- 不推送、不打 tag、不发 Release —— 需要单独授权。
- 不改 `.github/workflows/*` 的通过条件。
- 不删测试、不改断言迁就实现、不把跳过写成通过。
- 不用 `git add -A`。
- 不建 `xxx-2` / `xxx-fix` 副本目录，并行只在 `D:/Projects/_worktrees/`。
- 不动 `docs/**/*.log`（每轮验收原始日志）。
- 提交身份走环境变量，不改全局 `git config`。
