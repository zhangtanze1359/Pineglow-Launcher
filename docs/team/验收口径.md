# 验收口径

> 这一份回答一个问题：**凭什么说"过了"。**
> 规则继承 `AGENTS.md`，这里只把判定档位和伪证形态写死。

## 一、四种判定档位（只允许这四种）

| 判定 | 含义 | 允许写的措辞 |
|---|---|---|
| **可闭环** | 我重跑了命令，输出与要求一致 | "已验证，见 `<文件>`" |
| **未处置** | 事实成立但没处理，或需要授权 | "未处置，原因：…" |
| **不可复现** | 我跑了，结果和要求不一致 | "不可复现，实际输出见 `<文件>`" |
| **未验证** | 我没有条件跑（缺环境、缺授权、缺设备） | "未验证，缺：…" |

**禁止的措辞**：「应该没问题」「大致一致」「基本完成」「根据执行者日志」「据了解」。
这四类一旦出现在验收报告里，整份报告作废。

## 二、证据的最低形态

一条判定 = 一个文件，文件里必须有：

```
$ <完整命令>
<完整 stdout / stderr>
exit code: <0 或 非0>
```

只有结论的 Markdown 不算证据。有截图但没有"用哪种方式截的"也不算。

## 三、"大致一致"为什么不行

历史上真实发生过：测试数与 `scripts/test-inventory.txt` 差几条被放过，后来发现是删了断言让门槛变绿。
所以现在是**双向断言**：清单里的每条必须在测试里找到，测试里的每条必须在清单里登记。差一条即 FAIL。

`node scripts/run-inventory-tests.cjs` 就是干这个的。

## 四、技术绿 ≠ 发布放行

两个结论必须分开写：

- **技术门槛**：`node scripts/gates.cjs` 四道门是否 exit 0
- **发布放行**：`FormalPhaseApproval`，默认 `NOT_GRANTED`

历史案例：六门槛全绿，但 `R5-04`（发布线遗漏）、`R5-05`（版本号仍是 1.0.0）未处置，
所以那一轮的结论是「技术门槛 PASS；发布放行 `NOT_GRANTED`」。这个写法是对的，不是矛盾。

## 五、反证：说明"咬得住"

只跑一遍绿只说明"没红"，不说明"能咬住错误"。关键断言至少一条变异实验：

1. 把实现改坏一处（例如删掉一个路由登记、签名校验短路）
2. 重跑该断言，**确认它变红**
3. 还原，确认重新变绿
4. 把三次输出都存进证据

反证在隔离副本里做，不许撤销用户工作区。

## 六、验证环境

| 项 | 要求 |
|---|---|
| 跑测试的位置 | `D:/Projects/_worktrees/<分支>`，**不是**主工作区（主工作区 309 条假失败是外部规则，不是代码问题） |
| PATH | `C:\Windows\System32;C:\Windows` 前置（否则 GNU `find` 抢 `.bat` 里的 `find`） |
| MSBuild 属性 | 只用 `-p:`，不用 `/p:` |
| 门槛数字真值 | `docs/baseline.md`，由 `node scripts/gates.cjs --baseline` 生成，别手改 |
| 原始日志 | `docs/**/*.log` 不许删，那是证据链 |

## 七、审查者身份

`REV` 不得是本轮任何任务的执行者。这不是流程洁癖：历史上一人既改又验，结论是"全绿"，
独立复核时发现断言被改写成恒真。

如果本轮只有一个人能干活，那这一轮的结论最多写到「执行者自评，待独立复核」，不许写「通过」。
