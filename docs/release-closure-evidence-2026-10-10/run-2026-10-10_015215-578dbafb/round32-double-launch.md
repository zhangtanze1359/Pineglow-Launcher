# 第 32 轮：双击启动两次会发生什么 —— 无单实例守卫，且**第二个实例完全没有日志**

运行标识：`run-2026-10-10_015215-578dbafb`（第 32 轮追加）
时间：2026-10-11 18:25–18:38，Asia/Hong_Kong（+08:00）
本轮性质：**只读审计 + 隔离夹具实测，产品目录零改动**（0 staged）。

---

## 1. 为什么查这个

「用户双击两次图标」是**最常见的操作之一**，而前 31 轮从没验过。审计先看有没有单实例守卫：

| 检查 | 结果 |
| --- | --- |
| `Mutex` / `SingleInstance` / `GetProcessesByName` 之类 | **全树没有** |
| `RunningInstanceRegistry` | 它管的是**游戏实例**（"运行中的实例不得被移除"），**不是启动器自身** |
| `LocalApiService.Start()` 里的 `_listener.Start()` | **没有 try/catch**，端口被占时异常直接抛到 `App.cs` 的 catch（那里只记一条日志然后继续） |

预测：第二个实例会绑定失败 → `WebShellWindow` 的健康检查失败 → 走**静态 UI 回退**（源码注释自己写着这条路是"界面看起来能用，但完全没有 API"）。

## 2. 实测：三个发现，其中两个比预测更糟

夹具：出厂 EXE + `portable.flag` + 沿用既有配置；**不设 `PINEGLOW_API_PORT`**，两个实例都用内置默认端口 48123——与双击两次完全一致。

### 2.1 两个窗口都在，而且第二个窗口**看起来完全正常**

| 观测 | 结果 |
| --- | --- |
| A / B 都存活 | ✓（pid 27236 / 30304） |
| 两个进程**各有一个可见窗口**，标题都是 `松光启动器` | ✓ |
| B 的窗口截图 | **与正常启动逐字节相同**（`E8D42C44…`） |
| B 的窗口里**显示着真实数据**（账号卡、9m 总游玩时长、7 个实例、四条真实资讯） | ✓ |

### 2.2 B **没有自己的 API**——它借用 A 的

决定性实验：杀掉 A，再看 48123 还答不答。

```
杀 A 之前：GET http://127.0.0.1:48123/  ->  200，6962 字节（token 0DDF4219…）
杀掉 A    ：A gone，B 仍存活
杀 A 之后：GET http://127.0.0.1:48123/  ->  无法连接到远程服务器
```

→ **B 没有 API。** 那 B 的界面为什么有数据？因为 `OnWindowOpenedAsync` 的健康检查打的是 **共享端口**，
而**A 会回答它**——检查通过，于是 B 的 `Web.Source` 被设成 `http://127.0.0.1:48123/…`，
**B 的窗口实际加载的是 A 的界面（带 A 的会话令牌）**。
（这一条是从证据推出的，不是直接观测到的；直接观测到的是"B 无 API 却显示真实数据"。）

### 2.3 最糟的一点：A 退出后，B 的窗口**外观毫无变化**

杀掉 A、等 20 秒后再截 B 的窗口：**哈希与之前逐字节相同**（`E8D42C44…`）。

即：后端已经死了，界面**看起来还是好的**（首页是一次性渲染，不会因为 API 消失而重绘）。
用户此时点任何东西都会失败，但**屏幕上没有任何线索**。

### 2.4 第二个实例**一行日志都没有**

夹具的 `data\logs\launcher-20261011.log` 全程只有 **2 行**（A 的启动 + A 的监听）：
**B 的启动行没有、`[LocalApi] 启动失败` 也没有。**

根因（`LauncherLog.cs:85`）：

```csharp
_writer = new StreamWriter(file, append: true) { AutoFlush = true };
```

`StreamWriter` 的默认共享模式是 `FileShare.Read`——**不共享写**。A 已持有当天日志文件，
于是 B 打开时抛 `IOException`，被 `RolloverLocked()` 的 catch 吞掉并把 `_writer` 置为 `null`；
此后 `Write()` 在开头 `if (_writer == null) return;` **直接返回**——**B 的所有日志调用静默失效**。

所以第二个实例**在最需要日志的时候（绑定失败）恰恰没有任何日志**。

## 3. 定性

| 维度 | 判断 |
| --- | --- |
| 是产品缺陷吗 | **是**（新增第 12 条） |
| 严重度 | **中**：不丢数据、不崩，但会得到一个**看起来正常、实际已死**的窗口，而且**没有任何日志可查** |
| 触发条件 | 启动器被启动两次（双击两次、或启动过程中再点一次） |
| 影响面 | 双窗口共享一个后端；先关掉其中一个会让另一个变成僵尸界面；排查时无日志 |
| 修复方向 | ① 加**单实例守卫**（命名 Mutex 或 IPC 唤起已有窗口）；或 ② 第二个实例检测到端口被占时**明确告诉用户**而不是静默借用；③ **日志文件改为 `FileShare.ReadWrite`**（或第二个实例另开文件）——这一条无论选①还是②都该做，因为"失败时没有日志"本身就是缺陷 |
