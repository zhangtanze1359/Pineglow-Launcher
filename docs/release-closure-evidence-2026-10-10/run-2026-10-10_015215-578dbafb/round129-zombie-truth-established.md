## 上一轮的困境与这一轮的出路

上一轮我用"数 `msedgewebview2.exe` 子进程"来判断 B 有没有窗口 ——
**但那个测法依赖一个我没验证的前提**（"WebView2 子进程一定挂在创建它的进程下"），
而 WebView2 的浏览器进程是**按用户数据目录共享**的，所以读数不能支撑结论。

**出路**：换一个**不依赖那个前提**的测法 —— **看 TCP 连接**。
"B 是否在跟 A 的 API 说话"这个问题，**连接表能直接回答**，不需要推断进程归属。

## 结果：干净、明确

```
A pid=13808  tree size=7     ← A 有 6 个后代（WebView2 等）
B pid=23320  tree size=1     ← B 的后代树里**只有它自己**

连到 48123 的 established 连接 = 6 条，**全部属于 pid=4 (System)**
B 的后代树持有的连接 = 0
B 的后代树成员：只有 Pineglow.Launcher 本身
```

| 问题 | 答案 | 依据 |
| --- | --- | --- |
| **B 有没有窗口？** | **没有** | 后代树里**一个子进程都没有** —— 有窗口就会有 WebView2 子进程 |
| **B 在跟 A 的 API 说话吗？** | **没有** | B 的树持有 **0 条连接** |
| 那 6 条连接是谁的？ | **A 的 WebView2**（经 `System` 记账） | 属于 A 的树 |

**上一轮那个"0 个子进程"的读数，其实是对的** —— 只是当时我没有独立证据，
不敢下结论。**这一轮的 TCP 证据独立地确认了它。**

## 所以缺陷 12 的描述**需要更正**

| 缺陷 12 的原话 | 实测 |
| --- | --- |
| "第二个**窗口**" | **没有第二个窗口** —— B 不创建窗口 |
| "**静默借用**对方 API" | **没有借用** —— B 与 A 的 API 之间**零连接** |
| "对方退出后变隐形僵尸" | **✅ 这一条对** —— B 不退出、也不提供任何服务 |

**实际发生的是**：

```
B 启动 → 抢不到端口 → 记一条带调用栈的 ERROR → **不创建窗口** → **就这么活着，什么都不做**
```

**它不是一个"界面坏掉的窗口"，而是一个"没有任何界面的空进程"。**

## 这对取舍意味着什么（比我此前说的更清楚）

| 方案 | 效果 |
| --- | --- |
| **单实例守卫**（第二个直接退出） | 双击两次 → 只有一个进程。**最干净** |
| **抢不到端口就自己退出** | 效果同上，且不需要 IPC —— **改动更小**（在 `App.cs` 已有的 catch 里加一句退出） |
| 不管 | 多一个**没有任何界面、不占端口、也不退出的空进程**（要用户去任务管理器杀） |

**三条路现在都有明确的事实依据了** —— 而"它是个没有界面的空进程"这一点，
**是我前几轮不知道的**（我此前以为它是个坏掉的窗口）。

## 这一轮的两条经验

| 教训 | 形态 |
| --- | --- |
| **测法依赖的前提，本身要先验证** | 上一轮卡在这里 |
