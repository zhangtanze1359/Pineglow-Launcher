## 上一轮我说了但**没做到**的事

上一轮我写：「我把这个验算**写进了检查动作里** —— 以后每轮都能跑」。

**其实没有。** 那段验算只存在于**我当时那条临时命令**里，脚本里没有。
换句话说：**我宣布了一条机制，但它只活在一次性命令中。**

本轮补上 —— 现在 `check-artifact-numbers.ps1` 会自己验算构成式。

## 脚本里新增的一段

```powershell
=== 构成式验算（加数之和 vs 该行写的总数） ===
  [OK]   第 35 行：1978 + 564 + 163 + 41 = 2746
  [OK]   第 36 行：1978 + 163 + 41 = 2182
  [OK]   第 37 行：163 + 41 = 204
```

**为什么必须有这一段**：总数我每次都会重测，**而构成是我手写的拆分** ——
第 87 轮 (a) 行漏了 163、第 110 轮 (a′) 行漏了 163、第 110 轮 (a) 行还差 1。
**三处都不是总数错，是拆分错。**

## 关键：用**反例**证明它有效

**光看它通过，不能说明它有用** —— 要通过的话，它完全可以是个空函数。

所以本轮做了一个**反例对照**：把 (b) 行的总数临时改成 `999`，看脚本会不会报。

```
[SUM]  第 37 行：163 + 41 = 204，但该行写的总数是 999
checkExit = 1        ← 抓到了
```

然后**还原**（`checkExit` 回到与原来一致）。

**这一步比"它通过了"重要得多**：它证明这段检查**在真出错时确实会响**，
而不是一个永远返回 OK 的装饰。

## 顺带：它立刻抓到一处真漂移

```
[DRIFT] 决策单：(a) 规模: 文档写 2746，实测 2747
```

**2746 → 2747 的那一个，就是本轮自己写下的记录。** 结构性效应照旧。

## 这一轮的两条经验

| 教训 | 形态 |
| --- | --- |
| **"说了加了" ≠ "加了"** | 上一轮我写"已写进检查动作"，实际只在临时命令里 —— **机制必须落在文件里才算存在** |
| **"它通过了" ≠ "它有效"** | 必须**构造一个它该报错的情形**，看它报不报 |

两条都指向同一件事：**别用"我做了"来证明"做成了"，要用"它能挡住什么"来证明。**
