## 判别设计

上一轮（记录 130）留下的冲突：**代码说窗口会被创建，而读数说没有渲染。**
我提了一个**假设**：WebView2 的用户数据目录是"每个应用一份、独占"的。

**判别方法**：给两个实例**各自一个可用的端口**（不同端口）。
- 若**两个都渲染** → 与端口无关、目录也不独占 → 假设不成立；
- 若**只有一个渲染** → 说明**即使端口没问题**，第二个也渲染不了 → 假设成立。

## 结果：**假设成立**

```
A 显式端口 49874   apiUp=True
B 显式端口 63082   apiUp=True          ← B 的端口**完全正常**

A: pid=30416  tree=7
    30416  Pineglow.Launcher
     4856  msedgewebview2
     9236  msedgewebview2
    31248  msedgewebview2
    15772  msedgewebview2

    31448  msedgewebview2        ← **6 个渲染进程**

B: pid=31144  tree=1
    31144  Pineglow.Launcher     ← **0 个渲染进程**
```

**而且夹具里只有一个 WebView2 用户数据目录**：

```
<fix>\Pineglow.Launcher.exe.WebView2\EBWebView
```

| 观测 | 结论 |
| --- | --- |
| B **有自己可用的端口** | 端口**不是**原因 |
| B **仍然 0 个渲染进程** | **渲染失败与端口无关** |
| 两个进程**共用一个** WebView2 数据目录 | **争用**是最可能的机制 |
| A 正常渲染（6 个子进程） | 先到者拿到目录 |

**所以：僵尸的根因是「第二个实例初始化不了 WebView2」**，而不是"抢不到端口"。
上一轮那个假设，**本轮被一个能把它证伪的实验支持了**。

## 对修法的影响（**改了**）

我此前推荐的是"**抢不到端口就退出**"（改动最小）。**现在这个方案是错的** ——
因为**第二个实例的端口是好的**，它**根本不会**走"抢不到端口"那条路。

**正确的形状是「单实例守卫」**：第二个实例在**创建窗口之前**就发现自己不该继续，
于是退出（或把第一个实例的窗口提到前台）。

| 方案 | 现在的评价 |
| --- | --- |
| 抢不到端口就退出 | **❌ 解决不了** —— 端口正常时不会触发 |
| **单实例守卫** | **✅ 对的形状** —— 在 WebView2 初始化之前拦掉 |
| 不管 | 多一个**空窗口壳 + 不退出**的进程 |

**这是一个"实验改变了推荐方案"的例子** —— 如果我没做这个判别实验，
我会推荐一个**在真实场景下不会生效**的补丁。
