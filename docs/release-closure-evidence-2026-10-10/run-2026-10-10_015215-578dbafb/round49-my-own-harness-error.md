## 1. 记录 48 的 FAIL 到底是什么

记录 48 我报的是"产品自己的流水线判定 FAIL，成因未查明"。本轮把判定块逐字打出来：

```
快照文件数    : 312
失败项        : 2

 - 快照内存在 bin/obj，冷构建前提被污染

```

**两条真失败，都不是产品问题：**

| 失败项 | 成因 |
| --- | --- |
| `快照文件数量不符: 期望 475 实际 312` | 我给副本 `git init` + `git add -A` 时**副本里没有 `.gitignore`**，于是把 `bin/`、`obj/` 一起提交了 → `git ls-files` 变成 312 条（真实仓库是 312 条 tracked + 白名单，期望值按那个口径算成 475）→ 两边口径对不上 |
| `快照内存在 bin/obj，冷构建前提被污染` | 同源：没有 `.gitignore` 就把生成物当成了受跟踪文件 |

**第三条 `[已知边界·未通过]`（step9）不是失败**——脚本头部自己写着：

> 「该步骤记为 KNOWN-UNLOCKED（未锁定发布边界），**不是通过，也不阻断判定**。」

出厂版的历史运行里它同样存在，而判定是 PASS。

**所以：记录 48 的 FAIL 完全由我准备副本的方式造成。**

## 2. 我上一轮的"假设"错在哪

2. 真失败是我夹具的口径问题，**与 C、与十二条补丁都无关**。

而且我当时**明确标注了"这是未经验证的假设"** —— 这次标注救了场：如果我把那句假设写成结论，
报告里就会留下一条"十二补丁让产品自己的流水线失败"的**假警报**。
