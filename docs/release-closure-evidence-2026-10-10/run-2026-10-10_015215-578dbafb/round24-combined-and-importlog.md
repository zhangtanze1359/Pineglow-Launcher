## 2. 现场测量暴露了我自己补丁的一个毛病，然后改掉了

### 2.1 先证明 P-IMPORTLOG 有效

用合并构建的 EXE 起一次真实导入，观察 150 秒，读产品自己的日志文件：

| 构建 | 日志总行数 | `[Import]` 行数 |
| --- | --- | --- |
| **修复前**（第 21 轮，40 分钟导入） | **2** | 0 |
| 第一版 P-IMPORTLOG | ~3,206 | **3,204** |
| **加节流后（本轮定稿）** | **200** | **198** |

第一版确实解决了"完全空白"，但**引入了一个新毛病**：字节级下载进度每秒来 20 多次，全被写进了持久日志——
150 秒 3,204 行，一次 40 分钟的导入会产生**几万行**。这不是"日志详细"，这是**日志垃圾**。

### 2.2 改法

只对"字节进度行"做节流（正则匹配 `数字 单位 / 数字 单位`），**每秒最多一行**；步骤类消息一律照写：

```csharp
private static readonly Regex ImportProgressTick = new Regex(
    @"\d+(\.\d+)?\s*(B|KB|MB|GB)\s*/\s*\d+(\.\d+)?\s*(B|KB|MB|GB)", RegexOptions.Compiled);
// 进度行 1 秒 1 条；步骤消息不受限
```

节流后的日志**既短又真的有用**（原文摘录）：

```
[Import] 识别整合包：d7-fabric 导入，Minecraft 1.21.11，Fabric 0.19.5，0 个客户端文件
[Import] 扫描 Java 开始
[Import] 未找到 Java 21，正在自动下载...
[Import] 正在下载 Java 21：3.1 KB / 46.7 MB
[Import] 正在下载 Java 21：572.7 KB / 46.7 MB
[Import] 正在下载 Java 21：3.9 MB / 46.7 MB      ← 每秒一行，能看出速率
[Import] 正在下载 Java 21：23.3 MB / 46.7 MB
[Import] 库 107/107: slf4j-api-2.0.17.jar
[Import] 库文件进度 70/75
[Import] 库文件进度 75/75
```

**16 倍降噪，而且信息量更大**（原来 3,204 行里 99% 是同一个数字在变）。

改完之后重新走了完整验证：**947 通过 / 0 失败，build 0 警告 0 错误，锁定发布 exit 0**。

## 3. 又一次被 BOM 绊倒（这次加了防线）

本轮第一次合并验证时，`apply-proposed-fixes.ps1` 的 P-FAKEIP 步骤报「0 匹配」，而**同一脚本里纯 ASCII 的锚点全部正常**——这个组合就是 BOM 丢失的指纹：
PowerShell 5.1 按 GBK 读没有 BOM 的 `.ps1`，脚本里的**中文锚点变成乱码**，于是静默失配。

这已经是这个会话里**第五次**同一类问题。所以本轮给两个补丁脚本都加了自检：

```powershell
$selfBytes = [IO.File]::ReadAllBytes($PSCommandPath)
if (-not ($selfBytes[0] -eq 0xEF -and $selfBytes[1] -eq 0xBB -and $selfBytes[2] -eq 0xBF)) {
  throw "本脚本缺少 UTF-8 BOM：PowerShell 5.1 会按 GBK 读取它，脚本里的中文锚点会静默失配。请先补回 BOM 再运行。"
}
```

并做了自测：把 BOM 剥掉的副本确实**拒绝运行**。
