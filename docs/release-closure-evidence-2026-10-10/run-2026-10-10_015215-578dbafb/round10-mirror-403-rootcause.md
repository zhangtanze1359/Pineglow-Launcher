## 1. 第 9 轮遗留的「镜像下 403」已定因：请求缺少 User-Agent

用**产品同代运行时**（.NET 10，`net10.0`）建最小客户端，对同一个镜像 jar 地址发 GET：

| .NET 10 客户端配置 | 结果 |
| --- | --- |
| 跟随跳转（默认）、无代理 | **403**（响应体 206 字节） |
| 不跟随跳转 | 302（跳转目标为 `cmcc.mirrors.ustc.edu.cn/bmclapi/...`） |
| 跟随跳转 + 走 127.0.0.1:7897 代理 | **403** |
| 对照：官方 `maven.fabricmc.net` 同路径 | **200**（1,984,980 字节） |

再用 `curl` 对同一条镜像 URL 做对照（同一时刻、同一网络）：

| curl 请求头 | 结果 |
| --- | --- |
| curl 默认 UA（`curl/8.x`） | **200** |
| **移除 User-Agent**（`-H "User-Agent:"`） | **403** |
| `-A "Mozilla/5.0"` | **403** |
| `-A "PineglowLauncher/1.0"` | **200** |
| 对照：官方地址（curl 默认 UA） | 200 |

两边一致：**镜像后端（BMCLAPI → USTC 跳转目标）对「没有 User-Agent」的请求返回 403**，
而 `System.Net.Http.HttpClient` **默认不发送 User-Agent**——这正是产品在镜像下拿 403 的原因。
官方地址不要求 UA，所以只在**选择镜像**时才暴露。

> 附带观察：`Mozilla/5.0` 也被 403，说明后端还有一条针对浏览器类 UA 的规则；这不影响结论——`curl` 的 UA 与一个启动器风格的 UA 都能拿到 200，只要**带一个非空、非浏览器类 UA**即可。

**影响面（已实测收窄）**：不是「镜像下载普遍失败」。本轮另做了一次**空目录 + 镜像的全新安装**：
`POST /api/sources/select {"key":"bmclapi"}`（返回 `selected=bmclapi, useMirror=true`）后安装 1.7.10——
**成功**，`completed`，130 秒，落盘 1 个客户端 jar + 33 个库 + 674 个资源对象（`d-install-mirror/install-install.json`）。

所以：**常规的镜像下载（Mojang 元数据/库/资源）没有问题**；携带 UA 要求的只是**被跳转到 USTC 后端的那类路径**，
本轮的实例是 Fabric 的 `/maven/...`。这与我上文的推断（"任何走镜像的下载都可能命中"）不符，**以实测为准**。

**修复方向（一行量级）**：给产品用于下载的 `HttpClient` 设置一个非空、非浏览器类 User-Agent
（在 `CreateApiHttp` 里设置一次即可）。这是候选清单里成本最低的一条，且能同时消掉 Fabric 镜像路径的 403。

## 3. 本轮我自己的工具失误（一处，已作废相关读数）

`curl -A "" -o NUL ...` 这一组读数**不可信**：Windows PowerShell 会把空字符串参数丢掉，
于是 curl 把后面的 `-o` 当成了 `-A` 的值、`NUL` 当成了目标，`-o` 从未生效——结果把 1.9 MB 的 jar 二进制打进了输出。
该组数据**已作废**，第 1 节表格只采用三个可信读数（移除 UA / 浏览器 UA / 启动器风格 UA）与 .NET 10 的四个读数。
正确写法是 `-H "User-Agent:"`（要移除时）或给一个非空值。
