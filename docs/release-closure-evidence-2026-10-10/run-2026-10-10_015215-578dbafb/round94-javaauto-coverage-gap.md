## 为什么要做这个回归

P-JAVAAUTO 改的是 **`ResolveJavaPath`** —— 而它在**启动路径**上（每次点"开始游戏"都会走）。
此前的四种加载器启动验证是在 **13 条补丁**的构建上做的，**早于这个补丁**。
所以"启动路径有没有被改坏"是一个真实的回归风险。

## 结果：**没能验成**（夹具的 Java 不见了）

```
prelaunch ok=False errors=1
   err: Java 运行时不存在：C:\Users\...\pineglow-jre-92310fa5...\jdk-21.0.12.1+1-jre\bin\javaw.exe
launch -> HTTP 500
```

夹具配置里的 `JavaPath` 指向 `%TEMP%` 下一个**已经被清掉的** JRE（早前轮次装的）。
**所以这次跑的根本不是"Java 找得到"那条分支** —— 回归检查**不成立**，
我不能拿它说"启动路径没问题"。

## 但它撞出一件事：**P-JAVAAUTO 覆盖不到这个分支**

`ResolveJavaPath` 的前两个分支是**不做存在性检查**的：

```csharp
if (!string.IsNullOrWhiteSpace(instance.JavaPath)) return instance.JavaPath;   // ← 直接返回
if (!string.IsNullOrWhiteSpace(config.JavaPath))   return config.JavaPath;     // ← 直接返回
// 之后才是扫描 → 找不到 → P-JAVAAUTO 的自动安装
```

**P-JAVAAUTO 只在"扫描一个 Java 都没找到"时生效。**
而"**配置里写着一个路径、那个路径后来没了**"（换机器、清了缓存、卸载了 JDK）会**在第一行就返回**，
**永远走不到自动安装**，于是启动 500。

**这是一个真实且常见的情形**：用户以前指定过 Java，后来那个 JDK 被卸载/移动了。

## 好消息：这一路上的两个改进都生效了

| 改进 | 表现 |
| --- | --- |
| **`prelaunch-check`**（不是 P-APILOG，是原有的） | **正确报错**：`Java 运行时不存在：<路径>` —— 诊断面在这个分支上是好的 |
| **P-APILOG** | 那次 500 会带完整异常与调用栈进日志（第 55 轮已验证该机制） |

所以这个分支**不是"静默失败"**，只是**没有自动恢复**。

## 这算新缺陷还是补 P-JAVAAUTO？

**两者都有一点，我把它记为 P-JAVAAUTO 的覆盖缺口**（而不是第 16 条缺陷）：
- 从"产品行为"看：配置里的路径失效 → 报错清楚、日志完整，**没有违反 README 承诺**（承诺是"自动检测与自动安装"，而"检测"确实发现了问题）；
- 从"我这个补丁"看：**它只覆盖了一半的入口** —— 扫描分支覆盖了，配置分支没有。

**修法很明确**：把前两个分支改成"**存在性检查通过才返回**"，让失效的配置路径**落到扫描+自动安装**那条路上去。
这是一行到两行的改动，下一轮可以接着做。
