## 一、版本目标与基线

**将 v1.1.0 定位为“存档保护与日常管理体验”功能版，集中完成五个任务包。** 用户能感受到的主要变化是：误删存档可以找回、退出游戏后自动备份、批量检查与更新 Mod、启动问题有明确处理入口。

以已发布的 [v1.0.3](https://github.com/zhangtanze1359/Pineglow-Launcher/releases/tag/v1.0.3) 为基线，规划时核实的远端源码为 `30f7b56e97370246628c7a1df6276af8c02fdb86`。Mod 删除恢复、单个 Mod 替换回滚、实例移除时保留文件、启动前检查均已有实现，本版围绕这些能力补齐体验。

正式支持范围继续为 **Windows x64**。Cleanroom、Legacy Fabric、整合包格式互通、主题系统和通用 AI 聊天留到后续版本。

## 二、五个主要任务包

### 1. P0：存档删除可恢复，统一备份与恢复入口

当前存档删除仍直接删除目录，是本版优先处理的数据保护缺口。

- 将“删除存档”改为移入应用恢复区，操作前展示世界名称、所属实例和占用空间。
- 为完整存档目录增加恢复能力，沿用既有恢复记录和路径校验机制，保留旧 Mod 恢复记录的兼容性。
- 在存档页提供统一入口，查看手动备份、自动备份和已删除存档，展示时间、来源、大小及实际状态。
- 恢复默认保留现有世界；同名冲突时恢复为副本。备份查询失败必须显示错误和重试入口。
- 提供手动清理：先展示选中条目及释放空间，再确认永久删除；恢复区不自动清空。

**完成标准：** 存档删除后重启启动器仍能找回；同名恢复不覆盖现存世界；跨卷、文件占用、磁盘不足和中断不会造成源文件与恢复副本同时丢失。

### 2. P1：按实例启用退出后自动备份

按已确定的偏好，自动备份在游戏退出后执行。

- 在实例设置中增加自动备份开关，旧实例默认关闭。
- 游戏进程退出后，检查该游戏目录下有变化的存档并生成独立备份；没有变化时跳过。
- 复用现有 ZIP 备份格式，增加临时文件、完整性校验和结果记录；成功后才更新“已备份”基线。
- 展示准备、备份中、成功、失败和取消状态。异常退出后的备份单独标注，不覆盖此前备份。
- 开启“游戏退出后自动关闭启动器”时，等待备份完成再关闭；失败时保留窗口和重试入口。
- 默认在每个游戏目录的备份与恢复区合计达到 **5 GiB** 时提醒，由用户手动清理。

**完成标准：** 正常退出、异常退出、无变化、备份失败、取消和自动关闭均有正确结果；备份期间再次启动同目录游戏会被协调等待，避免一边写存档一边打包。

### 3. P1：Mod 批量检查更新、确认更新与逐项撤销

复用现有版本查询、替换和恢复服务，补齐 Mod 管理界面的完整流程。

- 增加“检查更新”，展示当前版本、候选版本、来源及兼容信息，支持逐项勾选。
- 首版支持具有可靠在线来源信息的 Modrinth、CurseForge Mod；无法识别来源的本地文件明确标记。
- 默认检查适配当前 Minecraft 版本和加载器的稳定版本；不自动跨版本、跨加载器或降级。
- 更新前检查依赖风险；提交替换时保留原启停状态、在线元数据和旧文件恢复记录。
- 批量更新逐项提交。某项失败后停止尚未执行的项目，保留已成功结果并提供逐项撤销；取消停止后续项目。
- 游戏运行、二分定位或同目录文件操作进行中时，拒绝冲突更新，并说明原因。

**完成标准：** 校验失败不动旧文件；替换失败如实报告回滚结果；更新后的版本信息与磁盘文件一致；取消、失败或重启后可以辨认实际完成了哪些项目。

### 4. P1：启动检查增加明确的处理入口

在现有启动前检查上增加结构化问题和操作引导。

- 对 Java 缺失或不匹配、游戏文件缺失、目录不可用、内存配置风险提供独立问题项。
- 为可处理的问题提供对应入口：选择或安装 Java、前往安装或修复游戏文件、打开实例设置调整内存和目录。
- 修复完成后重新检查，由用户再次确认启动；警告继续保留“查看详情”和“继续启动”。
- 检查超时或失败时保留重试入口，不将未知状态显示为检查通过。
- 首页和实例页复用同一流程，保持实例身份、忙态、重复点击保护和离页后的响应处理一致。

**完成标准：** 从“发现问题”到“进入处理界面”再到“重新检查并启动”可以完整走通；处理操作作用于用户原先选择的实例。

### 5. P0 发布门槛：收拢现有改动，完成交付稳定性收尾

- 从发布基线建立隔离分支，分别核对并迁入已有图标、启动动效和启动参数重构；保留原工作区与历史证据。
- 统一应用品牌图标，复验 EXE、真实窗口、任务栏、Alt-Tab、favicon 和界面品牌区域；有对应快捷方式时一并检查。
- 处理规划时发现的 Linux 全量测试既有失败，先区分测试夹具、平台差异和产品缺陷，再作最小修复；保持 Windows 恢复和路径边界要求。
- 修复 Gitee 镜像流程对空响应、无效 Release ID 和上传失败的判断，重新验证客户端主源及 GitHub 备用源选择。镜像继续作为可选渠道，如实报告失败状态。
- 更新版本号、功能矩阵、API 文档和发布说明，清除仍把旧发布失败描述为当前状态的正文说明。

**完成标准：** 同一候选源码完成规定测试、构建、单文件冷启动和真实 WebView 验证；更新清单、版本、附件大小及 SHA256 一致；镜像状态与实际结果一致。

## 三、接口与兼容约束

- **恢复与备份：** 扩展现有恢复记录以支持存档目录，并增加备份来源和任务状态；旧 ZIP、旧 Mod 恢复记录继续可读，避免强制迁移游戏数据。
- **实例配置：** 增加自动备份设置；旧配置缺省为关闭。备份与恢复区保持手动清理策略。
- **Mod 更新：** 增加检查、执行、状态查询和取消能力；服务端依据来源与版本标识下载，复用现有替换和恢复路径。
- **启动检查：** 在现有响应上追加问题代码、严重程度和处理动作，保留 `errors`、`warnings` 的兼容性，前端不解析中文错误文本来判断动作。
- **文件协调：** 以实际游戏目录协调启动、备份、恢复和 Mod 写入，覆盖多个实例共享目录的情况。
- **前后端一致性：** API、live/mock、中英文本及文档随对应任务同步完成；业务逻辑继续放在服务层。

## 四、执行顺序与验收

**顺序：基线整理 → 存档恢复 → 自动备份 → Mod 更新 → 启动引导 → 集成交付。** Linux 测试与镜像流程的定位可提前开展，最终在同一候选版本上收口。

每个任务包先完成聚焦验证，再进入相关回归；新增缺陷修复保留有效的 RED → GREEN 证据。最终验收覆盖：

| 层级 | 必须覆盖的场景 |
|---|---|
| 数据与服务 | 删除恢复、同名冲突、跨卷、占用、空间不足、损坏备份、进程中断，以及恢复后的文件一致性 |
| 生命周期与并发 | 游戏退出、自动关闭、备份取消、共享目录、备份中再次启动、重复提交 |
| Mod 更新 | 来源缺失、版本兼容、依赖风险、下载或哈希失败、替换与回滚失败、部分完成、取消与撤销 |
| 真实界面 | 本轮构建的 Windows WebView 中走通核心流程，检查忙态、错误重试、中英显示、键盘操作及图标表面 |
| 集成交付 | Node 清单与全量测试、Windows/Linux .NET 全量、既有三平台构建、独立单文件冷启动、更新源回退与清单校验 |

交付时分别给出技术验收结果、未验证项和发布准备状态。**本轮仅交付规划；实施终点为可独立验收的候选版本及证据包，提交、推送、标签与正式发布沿用后续明确授权。**
