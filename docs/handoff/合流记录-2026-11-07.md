### 4.11.3 为什么这不是「改断言迁就环境」

- 23 例里没有一条被删除、被 skip、被 `return` 提前结束，也没有 `Assert.True(true)` 之类空断言。
- 每处平台分支都断言了**两边的真实行为**：Windows 侧全部保留原期望（本地 1379/1379 仍是同一套语义），
  POSIX 侧断言的是「产品在该平台确实如此」的可证事实（`HasHandleLocks==false` 的自我声明、
  `GetInvalidFileNameChars` 的实际内容、unlink 不受打开句柄影响、`%(RecursiveDir)` 的实际分隔符）。
- 两例（#8/#9）刻意加了**通用契约**：不管平台，都不得出现 `GetInvalidFileNameChars()` 里的字符 ——
  平台分支只用于「哪些字符算非法」。
- #12/#13 是纯粹的**用例自身缺陷**（写死 Windows 分隔符 / 依赖大小写不敏感的输出目录副本），
  修的是查找方式而不是期望值。

### 4.11.4 记录在案但本轮**不改产品**的 POSIX 口径差异

`PathSafetyGuard.PathsEqual` 与 `FileRecoveryService.IsPathInside` 恒用 `OrdinalIgnoreCase`，
在大小写敏感的 POSIX 上比文件系统更宽松（`/tmp/Game` 会被判成 `/tmp/game` 的同一路径/子路径）。
理论后果：在 POSIX 宿主上 `IsPathInside` 可能把大小写不同的兄弟目录判成「在锚点内」，从而**放宽**写入边界。
本轮不动的理由：交付平台是 `win-x64`（`CurrentRid()` / 发布资产均如此），Linux 只承担编译+测试门槛；
擅自改产品的大小写口径会改变 Windows 上的既有行为，属于需要单独立项的产品决策。
用例里也不再把这个宽松口径写成「跨平台事实」（见 #3）。
