# OPEN-09 决定：接受旧 CurseForge Key 继续有效 · 2026-11-24

## 决定

**编排方选择「接受现状」（方案 C）**：不再尝试吊销旧 CurseForge API Key。

旧 Key（`$2a$10$G3lI…NWWjOCrG`）**继续在 CurseForge 侧有效**，且**仍在公开仓库历史中**。

## 为什么做这个决定

### 选项是有限的

| 方案 | 可行性 | 代价 |
| --- | --- | --- |
| A. 提工单让 CurseForge 吊销 | 唯一可能真正解决 | 成功后**所有未升级 v1.0.7 的用户 CurseForge 失效**；处理周期未知 |
| B. 反复 `Regenerate` 碰运气 | 未验证的猜测 | 可能无效；每次都会产生新 Key |
| **C. 接受现状** | 确定可执行 | 旧 Key 一直公开有效 |

**CurseForge 后台不提供「删除 Key」功能**——只有 `Regenerate`，实测 Regenerate 后旧 Key 仍有效。
这不是操作失误，是平台设计。

### 风险的实际量级

| 项 | 评估 |
| --- | --- |
| 旧 Key 可被谁获取 | 任何翻查 GitHub 仓库历史或已发布二进制的人 |
| 滥用需要什么 | 主动、有目的地去找（不是偶然暴露） |
| 滥用后果 | 消耗持有人的 CurseForge API 配额；**不涉及用户数据** |
| 项目用户规模 | 较小 |
| 已被滥用的证据 | **未观察到** |

## 已做的风险控制

1. **新版本不再携带旧 Key**：v1.0.7 起使用构建期注入的新 Key。
2. **源码树零字面量**，守卫已扩展到全仓库（`.cs` + 构建配置 + 文档）。
3. **本机副本已清理**（`.cindy-worktrees/`）。
4. **风险已完整记录**（[`../2026-11-24-key-audit/README.md`](../2026-11-24-key-audit/README.md)）。

## 复查触发条件（若出现以下情况，重新评估本决定）

1. **CurseForge 配额出现异常消耗**（观察 console 的用量统计）
2. **CurseForge 封禁该 Key**（届时所有旧版本用户会看到缺 Key 提示）
3. **平台新增删除/吊销入口**
4. **项目用户规模显著增长**（暴露面随之放大）
