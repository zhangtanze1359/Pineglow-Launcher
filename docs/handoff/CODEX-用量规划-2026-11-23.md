## 二、什么时候值得派 Codex

**只在这三种情况下派：**

1. **需要「另一个人重跑」**——验收规则要求「执行者≠裁判」，我自己的测试数字不能给自己签字。这类必须派。
2. **需要独立实验证据**——对方要在**它自己的工作树**跑出我没跑过的样本（如第 4 轮的 19 轮重跑）。这类最值。
3. **高风险改动的第二双眼睛**——涉及数据销毁、路径安全、并发竞态、发布一致性的改动。

**不要在这两种情况下派：**

1. **文档措辞反复打磨**——可以用自查代替：机器化抽数（`grep`/哈希/行号）+ 逐条回原始文件。
2. **上一轮 FAIL 后「再确认一次」**——如果 FAIL 内容不涉及新的实验证据，再派一轮只是买同一句话。

## 三、每轮派发前的硬性门槛

派之前必须能在脑子里答出这三句：

- [ ] **这一轮要拿到什么新东西？**（新的测试数字 / 新的独立判断 / 新的实验）
- [ ] **我自己能不能做？**（如果能，先自己做）
- [ ] **失败了怎么办？**（如果 FAIL 只会是措辞问题，那就不该派）

答不出第一句 → 不派。

## 四、额度预算（建议）

按 Plus 订阅的实际能力，建议：

| 用途 | 单事项上限 | 说明 |
| --- | --- | --- |
| 常规验收复核 | **1–2 轮** | 目标：拿到一次独立通过，不做无限打磨 |
| 高风险事项 | **2–3 轮** | 允许迭代，但每轮必须有新实验证据 |
| 文档类事项 | **0–1 轮** | 优先自查 |
| 同一事项的绝对上限 | **3 轮** | 到第 3 轮仍 FAIL 且都是措辞 → 停止，交编排方裁定 |

**OPEN-04 的 7 轮已远超此预算**，这正是本页存在的原因。

## 五、失败时的正确处置

复核 FAIL 后按这个顺序走：

1. **先分类**：FAIL 是「技术结论错」还是「记录不准」？
2. **技术结论错** → 必须修，且修完需要复核（这是复核的价值所在）。
3. **记录不准** → **自己修，且用机器化核对修**（不信记忆，只信 `grep` 的输出）。
4. **修完不等于要再派**。若上一轮已明确「技术观察可接受」，剩余分歧只是覆盖说明的措辞 → **交编排方签定**，不再消耗额度。

## 六、配额撞墙时的做法

- 三款模型同时返回「try again at HH:MM」= 账号级限额，**不是网络问题**。立即停止重试。
- 用后台 `until` 循环等到恢复时间，**不要**用连续短重试去探测（探测本身也计入额度）。
- 不要为了「多一个角度」同时派多个模型（`gpt-6.2-sol` + `gpt-6.2-astra` + `gpt-6.1-sol`）——它们共享同一账号额度，且撞墙时一起失败。

## 七、自查能替代复核到什么程度

**能替代：**

- 数字可从原始日志复算（`grep passed=` 求和、耗时均值、增幅百分比）
- 哈希、行号、调用点数量（`sha256sum` / `sed -n` / `grep -n`）
- 文档内部一致性（全文搜索同一概念的多种表述）
- 「推断」与「已证」的区分（逐句问：这句话的原始证据是哪个文件哪一行？）

**不能替代：**

- 独立的测试执行（我的数字不能给自己签字）
- 对「我没想到的失败模式」的发现（第 4 轮的重跑、第 7 轮的等待上界，都是我想不到的角度）
- 正式销项签定
