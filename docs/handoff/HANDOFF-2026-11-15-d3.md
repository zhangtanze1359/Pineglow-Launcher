## 二、② 退出后自动备份（第一期，本次实施）

### 2.1 数据模型

- `GameInstance.AutoBackupOnExit : bool`（默认 `false`，**实例级**，旧 config 未含该字段时为 false）。
- 不做全局总开关（范围外）；不做保留份数策略（范围外，但 §2.5 必须记录该风险）。

### 2.2 判定 / IO 分离（硬约束）

新增纯函数面，**不碰文件系统**，供单测直接调用：

```
AutoBackupPlanner.Plan(
    bool autoBackupOnExit,
    IReadOnlyList<SaveInfo> saves,
    DateTimeOffset now)
  -> AutoBackupPlan
```

`AutoBackupPlan` 至少回答：

- `ShouldRun`：开关关 → false；无存档 → false；否则 true。
- `Targets`：本次要备份的存档（`FolderName` 列表）。判定口径要写进注释并配测试：
  **只跳过明确为空的存档**（判定依据用 `SaveInfo` 已有字段，不许 `new DirectoryInfo(...)` 现猜），
  非空存档全部备份。
- 不做时间节流/去重（范围外），但 `now` 必须进签名，方便将来加节流时不必改调用方。

### 2.3 触发点（唯一一处）

`LocalApiService.Instances.Launch.cs` 的退出监听 `Task.Run` 内，在 `RecordPlaySession + SaveConfig`
**之后**、`autoCloseOnExit` 的 `Environment.Exit` **之前**：

1. 重新 `LoadConfig()`（不要用启动时的旧快照）；
2. 取该实例当前值 → `Plan(...)`；
3. `ShouldRun` 为 false 直接跳过（一条日志即可）；
4. 对每个 target 调 `new SaveBackupService(gameDir).CreateBackup(instance, save)`；
5. **单个失败不中断其余项**，也不得让退出监听抛出去（整段包在 try/catch，异常只记录）。

失败语义（必须写测试）：**备份失败不等于源存档被改动**——禁止在备份路径上做任何 `move/delete`。

### 2.4 前端

- 实例设置里加开关「退出后自动备份」；
- 文案走 `ui/js/i18n.js` 的键，**不许在 `launcher.js` 里硬编码中文**；
- 开关保存走现有实例保存通道，不新增端点（若确认必须新增，先在交付说明里写明理由）。

### 2.5 必须记录的已知风险

- 无保留上限：整包实例每次退出都为每个世界加一个 zip，长期会占空间。**本期不实现清理**，
  但必须在 `docs/handoff/合流记录-2026-11-07.md` 的证据段里写明「未做保留策略，后续需 M2-x」。
- 与「退出后自动关闭」并存的时序：备份可能比窗口关闭慢，`Environment.Exit(0)` 会截断它。
  处理方式必须**明确选一种**并写进注释 + 证据：要么先备份再退出（阻塞到备份完成、加上限超时），
  要么退出时不等备份（记录风险）。**不许两边都含糊。**

### 2.6 测试清单（至少）

| # | 用例 | 断言 |
|---|---|---|
| 1 | 开关关闭 | `Plan` → `ShouldRun=false`，退出后 `backups/` 无新增 |
| 2 | 开关开启 + 2 个非空存档 | 退出后两条备份都落在 `<游戏目录>/backups/<世界名>/` 下 |
| 3 | 源未损坏（失败路径 A） | 备份抛错时，**源存档内容与 mtime 不变**，其余存档仍被备份 |
| 4 | 失败可回滚（失败路径 B） | 备份失败后 `backups/` 下不残留半成品 zip；`RestoreBackup` 对旧备份仍可用 |

## 三、③ Mod 批量更新（第二期，本文件只定契约，实施在下一轮）

### 3.1 语义（来自交接书原文，逐条落到状态机）

> 「逐项提交；某项失败后停止未执行项、保留已成功结果并支持逐项撤销；取消停止后续项。」

状态机（纯函数部分必须是纯的）：

```
Pending → (执行) → Applied  | Failed
Pending → (取消) → Skipped
任一项 Failed ⇒ 其后所有 Pending 变 Skipped，且整体提前结束
```

### 3.2 契约草案

- `POST /api/instances/{id}/mods/batch-update`
  - 请求：`{ items: [ { fileName, sourceUrl?, sha1? } ] , cancel?: false }`
  - 响应：`{ ok, applied: [...], failed: { fileName, reason } | null, skipped: [...], undoId }`
- `POST /api/instances/{id}/mods/batch-update/undo`（`undoId`）
  - 逐项撤销已成功项；撤销前必须校验目标文件仍是本批次写入的那个版本（否则拒绝整批撤销并回报）。
- 取消：请求体 `cancel: true` 或独立端点；语义 = 当前项完成后不再启动后续项（**硬中断在项与项之间，不在项内部**，避免半写文件）。

### 3.3 纯函数边界

- `BatchUpdatePlanner.Step(state, result) -> next step`（可枚举、可单测）；
- `BatchUpdateUndoPlanner.Plan(applied, currentFiles) -> 可撤销项 / 冲突项`；
- IO（替换、备份旧 jar、写回）全部在服务层，判定不得直接 `File.Exists` 散落在 Planner 里。

### 3.4 测试清单（第二期）

| # | 用例 |
|---|---|
| 1 | 3 项全成：`applied=3`，undo 后三个文件都回到旧版本 |
| 2 | 第 2 项失败：`applied=1`、`failed=第2项`、`skipped=[3]`，且第 1 项的撤销可用 |
| 3 | cancel：已开始的项跑完，其余变 `skipped`，**无半写文件** |
| 4 | undo 冲突：目标文件被外部改动 → 拒绝撤销并回报冲突项 |
| 5 | 失败路径：源未损坏（替换前源 jar 未被删/未被改名） |
| 6 | 失败路径：可回滚（失败项不会留下 `*.disabled` / 临时文件） |

## 四、纪律（违反任一条即返工）

1. 判定逻辑抽纯函数，**IO 与判定分离**；Planner 里不许出现 `File.*` / `Directory.*` 调用。

4. 前端 i18n 走 `ui/js/i18n.js`，`launcher.js` 不许硬编码中文。
5. 不动 `dev/PineglowLauncher` 之外的构建脚本；不删 `scripts/_gen.cjs` `_migrate.py` `_batch_resources.cjs`。
6. 不推送、不打 tag、不改 `.github/workflows` 的通过条件、不放宽任何阈值。
7. 新端点必须在 `LocalApiService.Routing.cs` 登记（否则 `ApiRouteInventoryTests` 抓不到、文档对不上）。
